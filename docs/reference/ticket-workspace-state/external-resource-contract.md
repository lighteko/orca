# TW-04A External Resource Identity and Evidence Contract

**Status:** Decision draft for ticket-domain and Docker/IIS adapter owners. This records a recommended boundary; it does not freeze adapter-specific field names, change the `/v1` schema, authorize an effect, or assert that live adapters exist.

**Evidence pin:** Ticket source commit `2045808ffdb6baead2e659855cefb02f7b36491c`, tree `50d168f58db92c98b8e70cc32ed1dfbc1c5736a2`. Source observations below are from that pinned commit (`git show <commit>:<path>`), not the concurrently modified submodule worktree. The current `/v1` catalog is the contract source. The older package-default model and M0 resource-safety document are historical evidence only.

## Recommended boundary

Keep the ticket catalog as the durable resource ledger. Treat its `kind` as resource category and `intent.adapterId` plus `intent.adapterVersion` as adapter identity. Add strict typed Docker/IIS intent and per-resource observation variants, plus a separately versioned resource-universe observation that proves discovery scope and completeness. Cross-check typed resource evidence against the ledger's kind, execution domain, owner tuple, generation, and intent digest. Use `adapterId` as the closed discriminator for each ratified adapter variant and `adapterVersion` as a separately supported version; do not use a version string as the discriminator. The versioning/migration path for publishing those variants remains an explicit decision because current `/v1` validators reject unknown structure.

No Docker object decomposition, IIS site/app-pool mapping, host route, owner-marker format, or exhaustive discovery mechanism is settled by the available source. Do not fill those fields by copying the older default model or by interpreting the existing generic fixture as a supported production adapter.

## FACT — what the pinned `/v1` source establishes

- The catalog record contains `resourceId`, `kind`, owner `{ ticketKey, repositoryId, authorityId }`, `executionDomain`, `generation`, `intent`, lifecycle, attempts, and an optional last observation. `/v1` kinds include `docker-runtime`, `generated-compose`, `iis-site`, `iis-app-pool`, `dev-server`, `port`, and `test-lease`. The intent envelope contains `digestVersion`, `digest`, a free-form `adapterId` and `adapterVersion`, generic locator fields, and generic create-spec fields. The current generic locator values are scalar; create-spec values may also be arrays of strings. There are no typed Docker or IIS variants in this schema. See the pinned [resource schema](../../../ticket-workspace/packages/contracts/src/ticket-workspace-resource-v1.ts) and [catalog schema](../../../ticket-workspace/packages/contracts/src/ticket-catalog-v1.ts).
- `/v1` observations bind `resourceId`, `generation`, and `intentDigest` to an attempt/operation and record time bounds, presence, ownership, and optional acknowledgement/evidence digests. The resource validator requires the last observation's three identity values to match its ledger record. The observation itself has no typed Docker/IIS identity payload, explicit host, source/clock identity, or clock handoff; an opaque `evidenceDigest` does not state which checks or inventory scope were covered. The pinned contract has no resource-universe result or enumeration-completeness field, so one row observation cannot establish pagination, permissions, filters, truncation, or universe freshness.
- The semantic validator verifies the canonical intent digest, the ticket/repository/authority owner tuple, unique generations across active, tombstoned, and transition-prepared resources, unique attempt/operation pairs, and the rule that only an `isolated` repository may retain active external resources. It does not prove that the operating-system or service-side resource carries those claimed identities. See the pinned [semantic validator](../../../ticket-workspace/packages/contracts/src/ticket-contract-validator-v1.ts).
- A successful tombstone purge requires matching resource/generation/intent evidence and a successful completed teardown attempt with an `absent`, ownership-`match` observation and acknowledgement. The validator orders the observation during that attempt: `startedAt <= observedAt <= completedAt < validUntil`, through `timestampsAreOrderedV1`. Cleanup evidence references generations, attempt IDs, observation IDs, and residual resource IDs. Those checks establish ledger consistency, not an adapter's ability to enumerate every object in a Docker engine or IIS host. See the pinned [cleanup validator](../../../ticket-workspace/packages/contracts/src/ticket-cleanup-evidence-validator-v1.ts) and [timestamp ordering helper](../../../ticket-workspace/packages/contracts/src/timestamp-order-v1.ts).
- The pinned `/v1` corpus has a generic Docker runtime example (`adapterId: docker-slot`, with project/service/slot-like locator values) and generic scalar create-spec values. It has no typed IIS case. Corpus examples establish validator coverage only; they do not ratify a production adapter identity or prove that the sample maps to a real engine/site safely. See the pinned [schema corpus](../../../ticket-workspace/packages/contracts/fixtures/ticket-workspace-schema-v1.corpus.json).
- The older package default used `docker-slot` and `iis-site` intent discriminators. It modeled a Docker slot with project/service/slot, mounts, and ports; its IIS site intent included site name, app-pool name, binding host, port, and physical path. Its observations carried Docker container/project/service/slot/mount data or IIS site ID/name/app-pool/binding/path data plus a simple owner marker. It did not define an independent IIS app-pool adapter. This model is structurally different from `/v1`; these shapes are evidence of prior ideas, not normative `/v1` fields. See the pinned [older default contract](../../../ticket-workspace/packages/contracts/src/ticket-workspace-contract.ts) and [intent tests](../../../ticket-workspace/packages/contracts/test/ticket-resource-intent.test.ts).
- The older M0 safety note requires intent and generation to be durable before effects, a current ledger revision and exact-locator observation, per-attempt authorization, acknowledgement through CAS, and generation-bound detach before purge. It says verified absence can reconcile ledger state but cannot authorize destructive work. The controlled filesystem proof does not prove real Docker/IIS deletion; those adapters remain disabled pending non-cooperating-writer PoCs. See [resource mutation safety](../../../ticket-workspace/docs/resource-mutation-safety.md).
- The project already assigns ticket catalog/external-resource lifecycle to the ticket domain and worktree, agent, terminal, orchestration, and Orca mutation receipts to Orca. An Orca receipt cannot attest Docker/IIS success. The task graph gates TW-04B on both TW-04A and TW-05G, and TW-03's external-resource evidence on TW-04B. See [master plan](./master-plan.md), [review findings](./review-findings.md), and [task graph](./task-graph.md).

## RECOMMENDATION — compatibility and migration

- Keep existing `/v1` rows readable and preservable. Its resource `kind` set includes dev-server, port, and test-lease, and its adapter ID is not a closed enum. Apply a closed `(kind, adapterId, adapterVersion)` matrix only to ratified typed variants; do not globally reject unrelated or unknown generic rows. An unsupported row targeted by an operation is `unverifiable` and ineligible for mutation, while remaining intact in the catalog.
- Do not publish structured typed intent/observation data as a compatible in-place `/v1` extension. `/v1` uses strict objects and only scalar generic locator/create-spec values; `adapterVersion` versions adapter behavior, not the DTO shape. **Recommended durable-state policy:** leave `/v1` unchanged and put structured catalog changes under an explicit catalog schema version 2, with readers retaining v1 support. Keep the proposed universe result as its own named, versioned observation contract. A separately versioned, capability-negotiated artifact could replace catalog v2 only if its rollout, source pin, and old-reader behavior are frozen and tested first.
- Treat v1 generic rows as opaque legacy data until freshly observed. Never auto-convert the sample Docker row, infer typed identity from a name/path, or rewrite a generic `dev-server`, `port`, or `test-lease` row as part of Docker/IIS migration. A migration may attach typed semantics only after a current adapter read proves the exact endpoint, physical identity, ticket owner tuple, generation, and intent. If that proof is missing, preserve the old row and report the target unavailable; do not purge it or manufacture absence evidence.
- Do not emit v2 rows until the writer has a positive capability/version path proving the relevant readers understand them. Older strict readers must reject unsupported v2 or typed data safely; they must never silently treat a parse failure, unknown discriminator, or absent sidecar as an empty resource set.

## RECOMMENDATION — contract semantics to freeze after owner input

### Adapter and resource identity

1. Keep three identities distinct: resource category (`kind`), adapter implementation (`adapterId`, supported `adapterVersion`), and one resource incarnation (`resourceId`, `generation`, `intent.digest`). A new generation is required when the owned incarnation is replaced; reusing a name or path must not inherit the prior generation.
2. Define a closed supported mapping from `(kind, adapterId, adapterVersion)` to one typed intent and observation variant. Put the observation discriminator and observed adapter version in its typed identity-evidence payload, then compare them to the ledger intent. Reject unknown adapter IDs/versions, impossible category pairs, duplicate physical identities, and intent/observation cross-field mismatch. Preserve strict unknown-field rejection and canonical digest coverage of every field that changes the target or effect.
3. Use `resourceId` as a stable ledger identity chosen by the adapter contract, not as an undocumented claim that a physical object ID is known before creation. Typed intent must identify the exact target scope to be managed; typed observation must return the adapter's actual object identity and bind it to that intent and generation.

### Owner and host evidence

1. Bind ownership to the existing ticket tuple `{ authorityId, ticketKey, repositoryId }` plus the exact generation and intent digest. A positive `ownership: match` needs a machine-readable marker or equivalent service-side evidence that the adapter owner proves is unique to that tuple and incarnation. Names, paths, ports, Compose project names, IIS site names, and matching configuration alone do not prove ownership.
2. Treat `executionDomain` as the intended adapter host claim, not proof of where the client command reached. Each typed observation must carry or semantically bind the actual execution target and service endpoint identity used for that read. Docker needs the engine/context identity and actual engine host; IIS needs proof of the specific Windows machine and configuration authority read. The adapter owner must define stable identifiers and evidence sources for both.
3. The ticket authority's WSL host and a repository workspace host do not determine the external adapter host. A missing host/provider, route mismatch, unavailable service, unsupported execution mode, or uncertain endpoint yields `unverifiable`; never silently query another engine or machine. The shared plan's Windows/WSL MVP still needs an explicit supported route matrix, especially for WSL-coordinated Docker and Windows-native IIS.
4. `ownership: mismatch` and `unknown` remain distinct from `match`. A resource with no marker, a conflicting marker, a marker for another ticket/repository, or evidence that cannot be read must be preserved and reported as foreign or unverifiable; it is not eligible for teardown.

### Typed observation and completeness

1. Preserve the existing attempt-bound observation envelope and add typed identity evidence for the actual adapter target. Require consistency between presence and evidence state, actual host/endpoint, observed physical identifiers, owner proof, and the ledger record's resource ID, generation, and intent digest. A digest without its typed claims and covered scope is not enough for downstream semantic validation.
2. Define the observed universe before using an empty result. For Docker, the owner must state whether the adapter covers one container, a service/slot, a generated Compose project, or a larger set, and how all owned child objects are enumerated. For IIS, the owner must state whether sites and app pools are separate resources, how bindings and shared pools affect scope, and which objects enumeration includes. These are open choices, not inferred mappings.
3. A complete discovery observation must identify its host/endpoint and query scope, report completion (including pagination, filters, and access failures), and reject truncation, duplicate identities, permission gaps, or partial reads. The exact proof fields depend on the adapter API. Until that proof is defined and validated, report the universe as incomplete/unverifiable. A successful absence observation proves absence only for its exact target locator; an empty ledger array or partial service listing cannot prove that no external resource exists.
4. Keep exact-resource inspection distinct from universe discovery. `inspect` of a known ledger row may establish that row's state but cannot establish that no additional ticket-owned objects exist. Plan/cleanup projections must preserve unknown or out-of-scope residuals.

### Proposed versioned universe result

Add a separate `ticket-resource-universe-observation` result with its own `schemaVersion: 1`. This is a proposed TW-04A DTO; it is not present in the pinned package today, and the current per-resource `/v1` observation cannot substitute for it. The slots below state required semantics; exact field names and adapter-specific query variants still need owner ratification.

- **Source binding:** identify the ticket authority, ledger epoch/revision, ticket key, repository ID, adapter ID/version, and resource kind whose rows this read covers. A result for another ledger revision, ticket, repository, or adapter is rejected as mismatched.
- **Actual target:** identify the adapter query execution host and the actual resource authority/endpoint reached, each with stable host/endpoint identity and route evidence. Keep the process host distinct from the resource endpoint: a WSL process can query a Windows Docker engine, and an IIS observation must name the exact Windows machine/configuration authority read. A configured host or CLI context string by itself is not route proof.
- **Query scope:** include a strict adapter-specific description of resource families, selectors, filters, and collision domain, plus a canonical digest of the effective query. The scope must cover every object that could be owned by this ticket/repository and every foreign or unmarked object that could collide with the exact managed locators. A marker-only filter that hides collisions cannot prove a safe empty result. Do not put credentials in the DTO.
- **Capture and freshness:** the evidence-producing adapter/source owner creates `observationId` and immutable `ownerReadStartedAt` immediately before the first enumeration I/O. That same owner controls `observedAt`, `validUntil`, a source/clock-domain identity, and the maximum age. The caller may validate or reject freshness but cannot mint the ID, move the start time, or extend validity on receipt. Multi-page enumeration belongs to this one capture and its freshness window starts before page one.
- **Clock handoff:** all ordered timestamps must have a defined clock owner. When the evidence source, adapter process, ticket authority, or consumer is on another host (including WSL-to-Windows), do not compare their wall clocks as if synchronized. Freeze a bounded, authenticated clock/freshness handoff or use a source-owned freshness proof with a reviewed transfer rule. Without that rule, stale/clear evaluation across the host boundary is `unverifiable`; receipt time cannot make an old observation fresh.
- **Enumeration status:** report `complete`, `partial`, or `unverifiable` separately from resource presence. Include enough evidence to establish all pages/continuations were consumed, required read permissions were sufficient, no server/client limit truncated results, and returned physical identities are unique. Include the returned count and every typed item needed for ownership/collision evaluation; the count must agree with the item set. Report denied/unknown permission, continuation remaining/unknown, truncation, duplicate identity, page failure, and unstable/inconsistent listing explicitly. `complete` is allowed only when each required property is positively established.
- **Consistency:** the owner documents whether the source provides a snapshot-consistent listing or stable continuation token. If pages can omit/add objects during enumeration and no consistency or reconciliation rule closes that race, the result cannot claim a complete universe suitable for absence or cleanup decisions.
- **Items and limits:** enumerate every object in the declared scope, including foreign/unowned/unmarked collisions, with typed physical identity and owner evidence. Link any ledger-known object to its `resourceId`, `generation`, and `intentDigest`; a discovery-only object has no invented ticket generation. If an item/count/byte cap is reached, preserve the observed items as partial evidence and mark the result truncated, never complete.

**Zero-result rule:** `complete` plus zero returned items means only “no object matched this exact, fully read query scope at this observation.” It does not mean the Docker engine, IIS machine, or all external resources are empty unless the ratified scope explicitly covers that full universe and the adapter proves that scope. A zero returned by a filtered, permission-limited, paged-incompletely, truncated, stale, wrong-host, or non-snapshot-consistent read is partial/unverifiable, not absence. Exact-locator absence and complete-universe emptiness are separate claims.

**TW-03 rule:** per-resource observations may report a ticket-owned row's state. The production external-resource source must also provide complete universe coverage for each required adapter/endpoint scope, joined to the same ticket and catalog revision. Any missing scope or partial/unverifiable enumeration keeps the external-resource check unavailable/incomplete; it cannot be reduced to a clean result because the catalog array is empty.

### Cleanup safety and authority boundary

1. Retain intent-before-effect, durable attempt-before-effect, current-revision revalidation, exact-target observation, effect acknowledgement/CAS, and generation-bound tombstones. On CAS conflict or uncertain completion, reload and reconcile the same generation; do not replay an ambiguous destructive call.
2. Re-observe immediately before teardown and require exact host/endpoint, target identity, owner marker, generation, and intent digest to match. For group/child teardown, also require a fresh complete universe result for the exact approved scope. Delete only objects proven to be owned by that generation. Preserve shared, foreign, changed, unmarked, or unenumerated objects. Clean parent/child dependencies only in an owner-approved order with per-object receipts; an IIS site does not imply ownership of its app pool, and a Compose project does not by itself prove every child object is safe to remove.
3. Keep partial outcomes explicit: failed or unverifiable teardown retains residual IDs and evidence; contact loss is not absence; a tombstone is not evidence that purge completed. The pinned per-resource purge validator requires the absent observation during the teardown attempt; it is not a complete post-cleanup universe proof. Only matching target read-back plus complete scope read-back where required can support a successful purge record.
4. This resource contract grants no action-preview or mutation authority. Typed intent and observations are data/evidence only. A later effect still requires the separate TW-05G root gateway, current target-bound confirmation/capability contract, and TW-04B's adapter-specific admission and recovery. The task graph records the proposed one-use capability TTL as unratified.

## Bounded next implementation packet

After the ticket-domain adapter owner and the Docker/IIS execution owners answer the table above, make one ticket-repository-only contract change: freeze the version/migration path; add strict typed intent and per-resource observation variants for ratified Docker/IIS pairs; add the separate versioned universe-observation DTO and semantic validator; and update generated artifacts and corpora. Do not add Docker/IIS effect code or touch Orca runtime/UI/live resources in that packet.

**Acceptance:** strict typed variants for each owner-ratified adapter/kind/version, canonical digest coverage, actual host/endpoint proof, and a versioned universe result joined to the exact ticket/catalog revision. Discovery fixtures cover complete single/multi-page enumeration, complete zero, wrong or partial scope, hidden collision from marker-only filters, permission denied/unknown, continuation remaining, server/client truncation, duplicate identity, count/item mismatch, inconsistent pages, stale/future capture, caller receipt-time refresh, and wrong host/endpoint. Cross-host WSL/Windows fixtures remain unverifiable without a validated freshness handoff. Per-resource fixtures cover present/absent/foreign/unknown, wrong generation/digest, unknown adapter version, and concurrent change. Teardown fixtures prove shared/foreign/unmarked/unenumerated objects stay residual; tombstone success binds an absent observation captured within the successful teardown attempt, and group cleanup additionally requires complete in-scope read-back. Legacy generic v1 Docker/IIS/other-kind rows stay readable and intact; migration never infers typed ownership from a name. The supported old/new reader path, full semantic corpus, typecheck, and generated-artifact reproducibility must pass. No fixture may claim that read-only inspection authorizes a mutation.
