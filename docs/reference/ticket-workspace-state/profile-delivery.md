Status: **independently reviewed contract candidate**, 2026-09-30. This packet refines [TW-M1P in the Task DAG](./task-graph.md); it does not authorize installation or select a publisher. The TW-06P resident service artifact is a separate output. TW-06T production setup needs both artifacts.

## Proposed v1 contract

**Target.** Begin with one explicitly selected WSL2 Linux distro, one architecture/libc tuple, one effective Linux UID, and one profile artifact. Ubuntu 24.04 x64/glibc is a candidate, subject to an actual target probe and owner selection. Reject unsupported tuples; never choose the default distro implicitly. Do not rely on a system Node install.

**Publisher manifest.** A trusted publisher emits an immutable canonical manifest and detached signature. The manifest binds:

- manifest schema, delivery ID, source repository/commit/tree, lockfile, build workflow/image and target OS/distro/WSL/architecture/libc compatibility;
- exact Node version, upstream archive URL, filename, size, digest, and publisher-recorded verification of Node's signed checksum material;
- complete CLI/contracts/runtime package tarball closure with package identity, size, and digest;
- profile source/path, schema ID/version, profile ID/version, size, and digest;
- relative executable/profile entry points, compatibility versions, signing key ID and algorithm.

Orca verifies a trusted publisher signature and every artifact digest before transfer; the selected WSL target hashes received bytes again before extraction. The signature trust anchor must come from outside this manifest. Source commit/tree/lock/build fields and the publisher's upstream-checksum result are signed **publisher claims**, not an independently proven reproducible build. The current `0.0.0` package version is insufficient as release identity. Publisher keys, channel, revocation, and the profile artifact owner are **unselected**.

**Binding and enrollment.** Phase 1 installs a verified host/profile-bound **unbound base release** without an authority ID. It is usable only by a separately authorized, explicit authority issue/adopt flow; it cannot start a ticket service or claim production setup. Phase 2 explicitly binds a selected release to the existing authority ID and machine config after that flow succeeds, writing a new binding receipt without mutating the immutable release bytes. The receipts record manifest/artifact digests, profile schema/ID/version, machine ID, authority ID when bound, observed Windows host and selected WSL distro name/version, effective Linux UID, architecture and libc. Windows host and WSL registration identity remain **unproven**; observed names and IDs are an enrollment scope, not physical authentication. The owner must select stable evidence, threat limits and rebind behavior before wrong-host/registration claims become acceptance criteria. Orca rechecks the selected scope during explicit binding. TW-06T later rehashes installed Node/CLI/profile bytes before service launch or attach and authenticates the service hello against the bound tuple; a receipt alone is insufficient.

**Install and activation.** Only an explicit Orca setup action can preview and confirm the target/profile/release and owned file effects. A single writer fence scoped to the enrolled runtime root serializes install, authority binding, update, rollback and recovery; the fence's ownership and crash semantics need an implementation proof. Confirmation expires on target, manifest, profile, config, authority, or active-release change; recheck under that fence before writing. Stage verified artifacts under a product-owned ext4 runtime root separate from user config and ticket state. Use the exact bundled Node/npm 10 with a clean cache and locked local tarball closure; run offline with scripts disabled. Packed distributions must already contain verified executable `dist`/bin output because scripts will not build it. Verify executable versions and strict profile/config compatibility. One ext4 active-release record is authoritative; Windows keeps only an observation, never a second activation pointer. Write and sync candidate files and receipt, atomically replace the active record on the same ext4 filesystem, then sync its parent directory. This gives an ordered recovery protocol; rename alone does not prove durable cross-host transaction completion. Preserve the previous release. Do not edit `PATH`, shell startup files, user config, authority, catalog or ledger, and do not start a resident service in this task.

**Update and rollback.** Stage new immutable releases; never update an active global npm prefix in place. A profile/config mismatch leaves the candidate inactive. Rollback has a separate preview/confirmation bound to the current receipt and retained release, with host/profile/authority rechecks under the same single writer fence. Interrupted staging preserves the previous active release. On an ambiguous active-record write or sync result, retain both releases and report `unverifiable`; reread the sole ext4 active record and receipts during explicit reconciliation before any further activation. Windows observations never override that record; disagreement between its observation and the ext4 record is `unverifiable` until explicitly reconciled. Startup and snapshot reads do not repair or switch versions. A security-revoked release must not be a rollback target, subject to an owner policy still to be chosen. The atomic-visibility claim relies on same-filesystem rename semantics, while durability needs the explicit sync sequence; see [Linux rename(2)](https://man7.org/linux/man-pages/man2/rename.2.html).

**Read boundary.** Orca UI snapshot/status reads with missing or stale setup return unavailable without invoking WSL, Node, CLI, shell, service start, attach, or reconnect. This does not prohibit an explicitly invoked private CLI `status` command from running Node. TW-M1P delivers Node/CLI/profile provenance only. TW-06P separately delivers a pinned resident service artifact; TW-06T production setup joins and authenticates both. WSL-only delivery remains behind runtime platform checks; macOS, native Linux and SSH targets are explicitly unsupported in v1.

## Code-ready allocation: private release verifier

The first finite implementation packet is a private, pure verifier. It does not wait for production profile values, publisher identity, or production key: tests inject expected source/profile/target and a generated Ed25519 public key. Freeze this closed v1 manifest: schema ID/version, release ID, source repository/commit/tree/lock digest and build identity, target OS/distro/version/WSL version/architecture/libc/filesystem, Node/npm versions and archive metadata/upstream-checksum evidence, exactly four package records (CLI, contracts, Zod, `@noble/hashes`), profile metadata, CLI entry point, and signer `keyId`. Source, build, and upstream-checksum fields remain signed publisher claims; verification does not prove a reproducible build. The verifier result means “verified relative to the injected trust and expected values.”

- Manifest is at most 64 KiB of UTF-8, has no BOM or trailing bytes, and parses under strict Zod objects with no unknown keys. Its raw bytes must equal `canonicalJsonV1(parsedValue)` exactly. `schemaId`/version and OS/WSL/libc discriminator values are literals; IDs and key IDs are 1–128 ASCII `[A-Za-z0-9._-]` characters; version strings are bounded to 64 characters and validated by their owning schema; commit/tree are 40 lowercase hex characters; SHA-256 values are 64 lowercase hex characters; sizes are positive safe integers.
- Exact fields are all required: `schemaId="ticket-workspace-runtime-release"`, `schemaVersion=1`; `source.repository` is `lighteko/ticket-workspace`; `source.commit`/`tree`/`lockSha256` carry the hashes above; `build.workflow` is 1–256 printable ASCII characters, `runId` is a positive safe integer, and `imageSha256` is 64 lowercase hex. `target` fixes `os=linux`, `wslVersion=2`, `architecture=x64`, `libc=glibc`, and `filesystem=ext4`; `distroId` matches `[a-z0-9][a-z0-9._-]{0,63}`, while distro version and libc floor match bounded `major.minor[.patch]` strings and are compared with injected expectations. Node/npm and package versions use bounded semver strings. `node` contains archive metadata and upstream checksum-file SHA-256 plus the 40-uppercase-hex Node signer fingerprint. `profile` contains filename/size/SHA-256, `schemaId="ticket-workspace-profile"`, `schemaVersion=1`, and profile ID/version. `cliEntryPoint` is the source-declared `./dist/ticket-workspace-cli.js`; `keyId` is part of the signed body.
- The Node archive, four package tarballs, and profile are each a safe ASCII basename (1–160 `[A-Za-z0-9._+-]` characters, excluding `.` and `..`), unique across all six records, with no slash, backslash, absolute prefix, or traversal. Each is bounded to 512 MiB and their summed size to 1 GiB; the profile is bounded to 1 MiB. SHA-256 and byte count are recomputed from each supplied artifact. Each package SRI must be exactly `sha512-` plus standard padded Base64 SHA-512 of the same tarball bytes.
- The four package identities are the exact set `@lighteko/ticket-workspace-cli`, `@lighteko/ticket-workspace-contracts`, `zod`, and `@noble/hashes`, with no duplicates. Parse the profile bytes with the existing `TicketWorkspaceProfileV1Schema`; require its schema/profile ID/version to equal both the manifest and injected expected profile. Reject a validly hashed profile whose content disagrees with its metadata. Validate the relative CLI entry point against the private CLI package's declared `bin` target.
- The manifest carries a bounded `keyId`; `manifest.sig` is exactly 64 raw bytes (no text armor) and Ed25519 over the canonical UTF-8 manifest bytes. Resolve the key and revocation state only from injected trust input; do not fetch trust or read ambient configuration.

- **Owner/files:** private `ticket-workspace` source only: add `packages/contracts/src/ticket-workspace-runtime-release-v1.ts` and `packages/contracts/test/ticket-workspace-runtime-release-v1.test.ts`; add `packages/cli/src/ticket-workspace-runtime-release-verifier-v1.ts` and `packages/cli/test/ticket-workspace-runtime-release-verifier-v1.test.ts`. Reuse `canonical-json-v1.ts`, the strict profile schema, and Node's `node:crypto`; add no runtime dependency, workflow, Orca UI, or public contract.
- **Dependencies:** freeze the manifest fields and Ed25519 policy above; inject trusted keys/revocations and expected source/profile/target as verifier inputs. Use synthetic values and generated keys in repository tests. A production public key or profile is not a test prerequisite.
- **Acceptance and verification:** CI tests use small synthetic artifacts and an ephemeral Ed25519 key; accept a matching signed manifest and exact byte closure; reject malformed/unknown fields, noncanonical bytes, unknown/revoked key, bad signature, wrong source/profile/target, missing/extra/duplicate package or filename, profile metadata/content mismatch, absolute/traversal path, and size/SHA-256/SRI mismatch. Separately run one read-only positive replay against the retained C1 Node archive and four tarballs using a synthetic schema-valid profile, then confirm every input hash is unchanged; do not commit those binaries. Tests must prove the module performs no network request, child-process launch, extraction, install, profile write, authority operation, or ticket-state access. The verifier returns metadata verified relative to its injected trust/expectations; it does not publish or activate a release.
- **Implementation boundary:** this packet can proceed as a disjoint private-source worker after the manifest contract review. The existing private-repository release publisher can be added after its service identity is named. Staging, active-record switching, setup UI, host binding, authority binding, update, rollback, and service launch remain later packets; they do not gate verifier unit tests.

The first profile artifact remains an implementation output after the owner selects its policy values, rather than a missing file the owner must somehow supply. Likewise, production channel credentials and trust keys gate publication and real release acceptance, not the verifier's synthetic-key tests. The other ticket-workspace transport-budget, owner-composition, and admission/cache work can use their existing disjoint ownership; none depends on production publisher credentials.

This packet is only the unbound active-release state machine. It does not extract archives, install product files, bind authority, start a service, or change user configuration.

- **Recorded profile draft:** the resolver requires `1.0.0`; its fixture uses ID `sellmate`. Historical M1 keeps the same profile policy across user homes, while paths and credential references live in machine config. Recommend ratifying `sellmate@1.0.0`; fixture policy/distro values and the tested guest are not production choices. Sources: `ticket-workspace/packages/contracts/src/ticket-workspace-config-v1.ts`, `ticket-workspace/packages/cli/src/ticket-workspace-config-resolution.ts`, its fixture, and the M1 sections of the historical work plan/spec.
- **Owned files:** add `packages/cli/src/ticket-workspace-runtime-release-state-v1.ts` and its focused test. Reuse the release verifier, `SqliteProcessFence`, and `durablyReplaceTrustedLedgerV1`; do not change config, authority, ledger, catalog, protocol, or dependencies.
- **Implementation receipt, 2026-10-01:** complete locally at private `b556834`, with fresh Sol 6.1 code approval. Existing file caps required seven concrete source modules (state, state-ports, active-record, input, preview, apply, reconcile), one test and two test-only support modules. Independent regression passed 35; Root full contracts/CLI tests passed 59/273 with 45 CLI skips. No existing source, dependencies or operational files changed. The assumptions below remain injected contracts; this is not a real ext4 or restart-durability proof.
- **Record:** one canonical UTF-8 `active-runtime-v1.json` (4 KiB max) is the only activation pointer on the selected ext4 root. Exact keys: `schemaId=ticket-workspace-runtime-active`, `schemaVersion=1`, `state=unbound`, `manifestSha256`, and `profile={profileId,profileVersion}`. Derive release location from digest. Keep every immutable release directory; never delete the previous one. No Windows pointer or writes to config, authority, ledger, or binding receipt.
- **Trusted input:** the injected staged-input port returns immutable staged identity, raw canonical manifest bytes, raw 64-byte signature, and the exact six artifact byte arrays (Node archive, four package tarballs, profile). Core recomputes hashes and calls `verifyTicketWorkspaceRuntimeReleaseV1` with current externally supplied trust and source/profile/target expectations. It never accepts a caller DTO claiming `verified`. The staged identity/immutability guarantee is an injected store assumption; this state machine proves neither extraction nor installed-tree provenance.
- **Finite operations:** `operation` is `install | update | rollback`. Install expects active absence; update expects the exact active digest; rollback targets a retained, verified, compatible, non-revoked release. All operations require authority binding observation `absent`; `present` or `unverifiable` rejects. A bound runtime needs a later explicit packet.
- **Preview tuple:** bind operation, canonical runtime-root identity (root descriptor device/inode, ext4, expected UID and configured/observed distro), expected active observation (trusted absence with a shared root-scoped observation generation, or canonical record digest plus file incarnation such as device/inode), candidate manifest digest, policy snapshot/revision, binding observation, and recovery generation. Invalid bytes, permission/read errors, or unknown binding are never absence.
- **Confirmation/apply:** only the preview issuer creates an opaque, one-use confirmation over that full tuple. Apply consumes it under the same root fence, rechecks root identity, active incarnation/digest, binding, policy revision and raw candidate bytes, then publishes. Digest-only A→B→A previews, forged/replayed confirmations, operation changes, or policy changes conflict without writing. Trust input must remain stable through publication under the fence, or provide a revision check that linearizes immediately before rename.
- **Fence:** serialize all writers for one configured physical runtime root, independent of caller machineId, profile, authority, or operation. Use `SqliteProcessFence` rooted at the runtime-root descriptor with one fixed key and a constant `machineId` namespace label plus the single configured distro verified against the observed WSL name. Never accept caller machineId as the lock namespace. This does not prove cross-distro serialization; reject a root reachable through another unproven distro. Do not reuse the ledger-specific fence wrapper unchanged.
- **Publication/results:** call `durablyReplaceTrustedLedgerV1` unchanged with fixed destination `active-runtime-v1.json`; preserve its descriptor-relative write, file sync, rename, inode/device check, and directory sync order. Results are `activated | conflict | rejected | unverifiable`; reject only before publication when the active observation remains proven unchanged. A post-rename uncertainty, descriptor-close uncertainty, or fence-release error is `unverifiable`, never safe rejection, and blocks further mutation pending reconciliation.
- **Recovery barrier:** one trusted injected recovery guard is shared by every session for a root. Each new session requires explicit initial reconcile; an ambiguous publication/release marks the shared root `needs_reconciliation` and advances its generation, invalidating all sessions' confirmations. Apply checks the shared guard under the fence. Initial reconcile may have no attempt and reports observed absence/current verified record; uncertain-attempt reconcile carries old/new digests or a bounded receipt and returns `old | new | other | absent | unverifiable` plus current observation and incarnation. Invalid/unverified active state is unverifiable, not absent; unknown stays blocked. Reread is an observation, not proof of directory-sync durability; reconcile never repairs, switches, deletes, or starts anything. Durable restart receipts are deferred to a real backend proof.
- **Tests:** synthetic signed inputs and injected ports cover install/update/rollback; raw-byte re-verification; stale/forged/replayed/op-changed confirmation; A→B→A incarnation; policy and binding changes; caller machineId variation and competing per-root writers; missing/corrupt record or candidate; pre-rename failure; lost rename acknowledgement, sync and fence-release failures; new-session initial reconcile; uncertain old/new/unknown reconcile; and two sessions where S1 ambiguity blocks S2 under the shared root guard. Reuse the existing memory trusted-ledger filesystem/fence and CAS publication fault model, inspecting the active filename directly. Assert no release deletion, second pointer, extraction, process launch, or config/authority/ledger write.
- **Code-ready:** pure transition/preview/recovery policy and fake-port tests need no production key, profile policy, publisher, or host identity. No extractor/staging writer exists at this pin. Real ext4 adapter proof later needs explicit setup permission and selected WSL2 root/UID, then checks ownership/mode/symlinks/ext4 and sync/rename/readback. Production activation still needs ratified profile/trust/host policy and the separately authorized authority flow.

Scoped documentation check only; this packet authorizes no staging, active-record write, live ext4 probe, or product setup.
