# Coordinator folder, artifacts, enrollment, and root gateway

**Status:** Decision draft for TW-05 and TW-05G. This freezes no endpoint, wire message, token encoding, or implementation. It is not implementation authorization.

**Source baseline:** `ticket-workspace/` at commit `54477c2371094f1cbc438845fdfde0ca3584e2aa`, tree `d4ca9e56560ec642ae548756fb636018146ae887`.

Labels distinguish confirmed facts, project invariants, candidate recommendations, and decisions still needed. Older ignored work-plan and authority notes are context only; they are not a replacement for the pinned package or the shared state documents.

## Decision boundary

TW-05 defines the ticket-owned coordinator directory and document lifecycle, plus safe enrollment of an already-existing Orca root Run. TW-05G defines how a current root Run may authorize ticket-owned external effects and how Orca Run binding changes are excluded while those effects are in flight. These are separate implementation packets: TW-05 may finish folder, artifact, and enrollment work without implementing the effect gateway; TW-05G depends on TW-05's durable correlation contract.

## Evidence and current limits

### Pinned ticket source

- **FACT:** `TicketCatalogTicketV1Schema` has optional `coordinatorLocation` and `coordinatorRef`. Its `orchestration` object has required `executionHostId`, optional `runId`, and dispatch/request IDs. `artifact.revision` is an optional, format-unconstrained `IdentifierV1` beside `schemaVersion: 1`; neither field defines a document set, manifest, folder-ownership proof, or enrollment state. See [`ticket-catalog-v1.ts`](../../../ticket-workspace/packages/contracts/src/ticket-catalog-v1.ts#L63) and [`ticket-navigator-snapshot-primitives-v1.ts`](../../../ticket-workspace/packages/contracts/src/ticket-navigator-snapshot-primitives-v1.ts#L57).
- **FACT:** `WorkspaceRefV1`'s folder variant requires `executionHostId` and `repoId`; `identityKey` and `instanceId` are optional. Its git-worktree variant has a different identity tuple. Ticket workspace hosts are a closed `windows` / `native` / `wsl` union; Orca's host IDs are a separate type and include `ssh:` and `runtime:` forms. The host mapping is not supplied by equal strings or path equality. See [`ticket-navigator-snapshot-primitives-v1.ts`](../../../ticket-workspace/packages/contracts/src/ticket-navigator-snapshot-primitives-v1.ts#L33), [`ticket-workspace-common-v1.ts`](../../../ticket-workspace/packages/contracts/src/ticket-workspace-common-v1.ts#L16), and [Orca `ExecutionHostId`](../../../src/shared/execution-host.ts).
- **FACT:** The catalog schema is strict v1. The current CLI catalog reader rejects any other catalog version, and the current ledger CAS validates both current and candidate values through that v1 reader before writing a `TicketCatalogV1`. Adding `rootRunEnrollment` to v1 is rejected as an unknown field; a v2 writer would also be unreadable to current v1 clients. A catalog-version migration therefore needs an explicit reader/writer rollout and mixed-version policy. See [`ticket-catalog-v1.ts`](../../../ticket-workspace/packages/contracts/src/ticket-catalog-v1.ts#L81), [`ticket-workspace-catalog-validation-v1.ts`](../../../ticket-workspace/packages/cli/src/ticket-workspace-catalog-validation-v1.ts#L31), and [`trusted-wsl-ledger-cas-file-v1.ts`](../../../ticket-workspace/packages/cli/src/trusted-wsl-ledger-cas-file-v1.ts#L145).
- **FACT:** `admitTicketContractV1()` is fixture contract admission. A compatible fixture can yield `mutationAllowed: true`; the helper does not establish a live Orca caller, current Run binding, user confirmation, or durable binding fence. This result cannot authorize a live action. See [`ticket-contract-admission-v1.ts`](../../../ticket-workspace/packages/contracts/src/ticket-contract-admission-v1.ts#L12) and [`ticket-contract-admission-outcome-v1.ts`](../../../ticket-workspace/packages/contracts/src/ticket-contract-admission-outcome-v1.ts#L8).
- **FACT:** The pinned [`durable-ledger-and-coordinator.md`](../../../ticket-workspace/docs/durable-ledger-and-coordinator.md) describes CAS-backed, restart-reconcilable ticket resource operations. It explicitly excludes Orca integration and does not define coordinator folder/artifact lifecycle or the root effect gateway.

### Orca Run and folder seams

- **FACT:** Orca already has server-side compatibility-evidence primitives: `verifyOrchestrationCompatibilityCaller()` checks terminal/process incarnation, launch-token hash, pane, and host scope and returns a caller authority or `null`. However, `runCreate` and ordinary `runUse` use a compatibility-tolerant wrapper: missing evidence is accepted, and failed verification is not rejected unless it returns a mismatching caller. The separate `takeoverLegacy` path requires caller authority. `runCreate` then resolves the pane from request `from`. A ticket-specific boundary must require a non-null verified authority and compare it with the current coordinator Run; the existing ordinary calls do not do that. A stable pane or Run lookup alone does not prove a live caller. See [caller verifier](../../../src/main/runtime/orca-runtime-verify-orchestration-compatibility-caller.ts#L16), [`runs.ts`](../../../src/main/runtime/rpc/methods/orchestration/runs/runs.ts#L15), and [`run-scope.ts`](../../../src/main/runtime/rpc/methods/orchestration/runs/run-scope.ts#L21).
- **FACT:** `createRun()` creates a Run bound to the supplied server-resolved pane and unbinds other Runs for that pane. `bindRun()` changes the Run binding under a SQLite transaction. `unbindOtherRunsForPane()` clears another binding and increments its generation. Pane lookup uses Orca's pane-key equivalence rules. See [`run-create.ts`](../../../src/main/runtime/orchestration/db/runs/run-create.ts), [`run-binding.ts`](../../../src/main/runtime/orchestration/db/runs/run-binding.ts), and [`run-lookup.ts`](../../../src/main/runtime/orchestration/db/runs/run-lookup.ts).
- **FACT:** `consumer_generation` is stored on the Run row and changes with binding changes. Current Run-delivery code checks it to reject a replaced mailbox consumer. That behavior is useful for detecting a stale consumer; it does not hold a ticket effect open, coordinate with the separate ticket ledger, or prove effect quiescence after a crash. Do not treat the number itself as a durable external-effect fence. See [`run-delivery.ts`](../../../src/main/runtime/orchestration/db/runs/run-delivery.ts).
- **FACT:** `RunRow` has no `executionHostId` field. The verified caller authority carries a host scope, so ticket host correlation must be derived from server-owned runtime/host authority and pass an explicit mapping; it cannot be copied from the Run row. See [RunRow](../../../src/main/runtime/orchestration/types.ts#L43) and [verified caller authority](../../../src/main/runtime/runtime-terminal-contracts.ts#L137).
- **FACT:** Orca exposes `projectHostSetup.setupExistingFolder` and `folderWorkspace.create` runtime seams. The former routes through an SSH provider when the selected host maps to SSH; this is route selection, not a read-back proof of the actual storage object. `FolderWorkspace.executionHostId` is optional and renderer-owned, and `createFolderWorkspace()` does not populate it. The child workspace has its own ID and no Repo ID. Neither result alone is a host-qualified ticket folder reference. See [`project-runtime-rpc-methods.ts`](../../../src/main/runtime/rpc/methods/project-runtime-rpc-methods.ts), [`runtime-project-host-setup-controller.ts`](../../../src/main/runtime/runtime-project-host-setup-controller.ts#L94), [`folder-workspace-types.ts`](../../../src/shared/folder-workspace-types.ts#L25), and [`folder-workspace-operations.ts`](../../../src/main/persistence/restoring-sessions/folder-workspace-operations.ts#L54).
- **FACT:** `Repo` stores a Repo ID, path, kind, and optional host/connection stamps. `repo.add` omits a host ID; the registration matcher treats a null host as path-only match-any. `repo.create` deduplicates by path and creates on the serving process. `runtime:` can address a paired client while the runtime controller itself validates and reads the path locally. These calls do not prove the physical storage route or stable folder incarnation. See [`Repo`](../../../src/shared/repo-types.ts#L42), [`repo.ts`](../../../src/main/runtime/rpc/methods/repo.ts#L105), [`runtime-repository-registration-controller.ts`](../../../src/main/runtime/runtime-repository-registration-controller.ts#L30), and [`runtime-worktree-selection.ts`](../../../src/main/runtime/runtime-worktree-selection.ts#L44).
- **FACT:** Run-binding SQLite transactions cover Run database updates, then commit before returning to the caller. No inspected transaction or durable lock covers a ticket-ledger write or external adapter effect. `consumer_generation` can detect a stale consumer but does not hold that effect open.
- **FACT:** `orchestration.reset --all` runs a transaction that deletes `runs` and other orchestration state, then inserts the inspect-only legacy sentinel. It does not consult a ticket effect exclusion. See [`reset-methods.ts`](../../../src/main/runtime/rpc/methods/orchestration/runs/reset-methods.ts) and [`orchestration-reset.ts`](../../../src/main/runtime/orchestration/db/reset/orchestration-reset.ts#L21).

## TW-05 — folder, artifacts, and enrollment

### Scope and first-use choice

The ticket authority first validates the ticket tuple and current catalog revision. Before any directory or document write, show the exact target path, the server-verified Orca host/storage route, the proposed folder registration, and the exact versioned document allowlist. The user must explicitly choose **Create coordinator folder** for that reviewed target. No folder is created by opening a ticket, reading `plan`, or discovering state. Do not derive a path from the ticket key or `stateRoot` unless a product owner ratifies that convention; the pinned source does not define either as the coordinator-folder root.

The first-use operation accepts only a path that does not already exist. An existing file, directory, symlink/reparse route, unregistered same-path Repo, or path registered on another host is a conflict. Preserve it and ask for another target or explicit owner-reviewed recovery; do not silently adopt, merge, overwrite, or delete user content. Retrying the same interrupted operation may resume only when its operation ID, owner marker, route proof, and directory identity all match.

The nearest compatible Orca identity is `Repo(kind: 'folder')`: ticket `WorkspaceRefV1.kind = 'folder'` requires `repoId`, while `FolderWorkspace.create` produces a child workspace ID and no Repo ID. The current `repo.add` RPC omits host ID, and its host matcher explicitly treats a null host as path-only match-any. `repo.create` likewise deduplicates by path and creates on the serving process. Do not use either result as host or ownership proof. `projectHostSetup.setupExistingFolder` routes using a requested host value, but that caller value is not independent proof. A narrow Orca-owned read-back must return the exact Repo ID, `kind`, actual execution host, canonical path, storage-route identity, and folder-instance identity before writing the ticket reference. See [Repo type](../../../src/shared/repo-types.ts#L42), [repo RPC](../../../src/main/runtime/rpc/methods/repo.ts#L105), [registration controller](../../../src/main/runtime/runtime-repository-registration-controller.ts#L30), [host matcher](../../../src/main/runtime/runtime-worktree-selection.ts#L44), and [folder-workspace creation](../../../src/main/runtime/runtime-project-group-controller.ts#L122).

Candidate directory identity is the tuple `(authorityId, ticketKey, directoryInstanceId, canonicalPath, actualExecutionHostId, storageRouteId, storageObjectIdentity, repoId)`. An Orca-owned host service must resolve and read back the path on the selected route, reject symlink/reparse escape, and provide a stable storage-object identity across restart. The ticket authority writes a reserved owner marker containing `{ schemaId, schemaVersion, authorityId, ticketKey, creationOperationId, directoryInstanceId, storageIdentityDigest }`, where `storageIdentityDigest` is SHA-256 over the canonical verified route and storage-object identity. The marker digest is bound to the directory identity and saved catalog reference. The marker alone is not authentication and cannot prove the host or physical directory. A copied marker at a different storage identity must not match. This proof field is a proposal pending the Orca-owned storage-identity seam; without that seam, creation and adoption stay unavailable.

Map the tuple to the current folder reference only after verification: `coordinatorLocation` records the ticket-host/path claim; `coordinatorRef` requires non-empty `executionHostId` and `repoId`, and this workflow also requires `instanceId = directoryInstanceId` plus `identityKey = SHA-256(canonical verified directory tuple)`. The Orca owner, not the ticket renderer, supplies `executionHostId`, `repoId`, and storage proof. A future validator must require the fields for an enrolled coordinator even though the v1 folder reference permits `identityKey` and `instanceId` to be omitted. The ticket `TicketExecutionHostV1` and Orca `ExecutionHostId` are different types; their mapping and the actual local/Windows/WSL/SSH storage routes are not proven by a matching string, config entry, or path. No route falls back to local. Until the exact route is attested, this folder slice is unavailable on that route.

### Versioned allowlist and artifact manifest proposal

The pinned catalog has only `{ schemaVersion: 1, revision? }` for artifacts. It has no manifest, document IDs, file paths, content hashes, allowlist, or publication state. Freeze the artifact contract as two strict objects, without adding guessed document names:

```text
ticket-document-allowlist v1:
  allowlistId, allowlistRevision, documents[
    { documentId, relativePath, mediaType, required, maxBytes, writerPolicy }
  ], allowlistDigest

ticket-coordinator-artifact-manifest v1:
  authorityId, ticketKey, directoryInstanceId,
  allowlistId, allowlistRevision, allowlistDigest,
  manifestRevision, previousManifestDigest?, documents[
    { documentId, relativePath, mediaType, byteLength, contentDigest }
  ], manifestDigest
```

The allowlist is a versioned, ticket-owner-approved registry. Document IDs, exact paths, media types, size limits, and which of the user/ticket authority/root agent may write each document are **open product choices**: no current source settles them. Until one allowlist revision is ratified and shown in the first-use confirmation, publish no documents and report artifact setup unavailable. The manifest must contain every required entry and no unknown entry; IDs and paths are unique. Each path is canonical relative form under a reserved artifact area, with no absolute paths, `.`/`..`, alternate streams, or symlink/reparse traversal. Validate per-entry byte limits and media type before publication.

Use SHA-256 over raw file bytes for `contentDigest`; use SHA-256 over canonical JSON of the manifest fields excluding `manifestDigest` for the manifest digest. Store each immutable published revision under a reserved directory keyed by `manifestRevision`, and store its manifest by digest. Set the existing v1 `artifact.revision` to `sha256:<manifestDigest>` only after all files and the manifest have been read back and verified. `manifestRevision` increments from the currently referenced manifest revision and binds `previousManifestDigest`; never overwrite a published revision. Treat a non-empty revision as a manifest pointer only if it has the recognized `sha256:<digest>` form and the pointed-to manifest verifies. Any other non-empty value is opaque legacy state: do not publish files, replace the catalog pointer, or claim artifact success until a ticket owner ratifies a migration/retention procedure that preserves the old value and defines the initial manifest revision. Do not infer that revision from the legacy string or invent a starting revision. An absent/empty pointer may begin at manifest revision 1 with no previous manifest digest.

Publication is a staged saga, not a cross-store transaction. Before recording a publication operation or writing files, validate the current artifact pointer: if it is an unrecognized non-empty legacy value, fail closed under the rule above. Bind the operation `requestDigest` to the ticket tuple, expected catalog revision, exact prior artifact pointer (or its absence), prior manifest digest, directory identity, allowlist digest, and all planned document digests. Stage under an operation-specific path on the verified storage route. Require create-only writes and host-proven same-volume publication/read-back; if the selected filesystem cannot prove the required semantics, do not publish. After every file and the immutable manifest validate, CAS the catalog pointer and operation result together against the expected ledger revision. Leave the prior revision intact.

Retry is idempotent only for the same operation ID and request digest. Before catalog CAS, exact staged/published bytes may be verified and reused only while the exact prior artifact pointer and catalog base still match. A differing pointer—including an opaque legacy value—file, revision number, allowlist, directory identity, or newer catalog base is a conflict; do not overwrite or clean up the conflicting bytes. If a crash occurs before catalog CAS, leave unreferenced stage/revision data and report pending/recovery-required. After a lost acknowledgement, reread the operation record, catalog pointer, and filesystem: confirm success only when the operation ID/request digest and target manifest digest match; if the recorded prior pointer is still current, resume the same CAS; any other pointer state is a conflict requiring explicit reconciliation. Never claim atomicity across ticket catalog, filesystem, and Orca Repo storage. Keep previous revisions and the coordinator folder by default; deletion/retention is outside this packet.

### Root Run enrollment and rebind

The ticket flow enrolls an already-existing current Orca Run. It never starts an agent or creates a replacement root. If no root Run exists, direct the user to establish one through Orca's normal session flow, then restart enrollment. Current `runCreate` and `runUse` are not an enrollment authority: `assertCallerHandleMatchesEvidence()` returns when caller evidence is absent, and `runCreate` then resolves a pane from request `from`. A stable pane/run lookup does not fix that gap. Enrollment stays blocked until Orca supplies a strict server-side caller attestation derived independently of request `from` and confirms that the attested live terminal is the current coordinator pane for the current, non-legacy Run. See [run methods](../../../src/main/runtime/rpc/methods/orchestration/runs/runs.ts#L15) and [caller check](../../../src/main/runtime/rpc/methods/orchestration/runs/run-scope.ts#L21).

Proposed enrollment correlation for the next strict catalog version:

```text
rootRunEnrollment: {
  schemaId: "ticket-root-run-enrollment",
  schemaVersion: 1,
  enrollmentOperationId,
  runId,
  executionHostId,
  consumerGeneration
}
```

Require all fields together or none. Read `runId` and `consumerGeneration` from the current Orca Run/binding. Derive `executionHostId` from server-owned runtime/host authority, then validate the ratified mapping; `RunRow` does not carry it. Never accept these values as caller authority. Preserve the existing `orchestration.runId` and `executionHostId` correlation consistently; a next catalog version must reject disagreement. Do not persist pane/terminal handles or caller attestation as a substitute for fresh server verification. `consumer_generation` is only a binding-change detector: Orca increments it on rebind, but it is not a lock, effect fence, or proof of quiescence. The current ticket catalog is strict v1, so this additional record requires catalog v2 or a separately capability-negotiated versioned field; do not add it as an unnegotiated v1 field. See [Run binding](../../../src/main/runtime/orchestration/db/runs/run-binding.ts#L23) and [verified caller authority](../../../src/main/runtime/runtime-terminal-contracts.ts#L137).

For first enrollment, the user confirms the current ticket and Run tuple. The attestation service derives the Run, host route, and generation, and the ticket owner commits them with an `enrollmentOperationId` using the expected catalog revision. On retry, re-attest and read the current Run; the same operation/digest and exact tuple may finish idempotently. A changed Run, route, or generation is stale, not a retry target.

Rebind is a separate explicit user action. Show the old ticket correlation and the newly attested current Run, require confirmation, and CAS against the exact old correlation and catalog revision. Preserve the old Run and folder. A CAS conflict or lost reply triggers fresh ticket and Orca read-back; never silently replace the correlation or create another Run. This enrollment record does not serialize Run mutations against later effects; that exclusion is TW-05G and remains unimplemented.

### Ordered setup and recovery

1. **Preview:** Read and validate ticket/config/current catalog, including the artifact pointer before recording any combined folder/artifact operation. If artifact publication is requested and the pointer is an unrecognized non-empty legacy value, stop the combined operation before any mutation; a separately requested folder-only operation may proceed under its own operation record. Resolve a route using Orca-owned host authority. Show the exact nonexistent path, route/host, proposed folder registration, allowlist revision, and files to be created. Require the user's explicit create choice. No choices are inferred from `stateRoot`, ticket key, or the renderer's host field.
2. **Record operation:** Under ticket CAS, persist a `catalog` operation with expected ledger revision and digest of the complete requested folder/artifact operation. Reuse its operation ID only for byte-identical retries.
3. **Create and mark:** On the verified host route, create the target exclusively, obtain its storage-object identity, write the owner marker, and read back both. A race or pre-existing path is a conflict; preserve it.
4. **Register and verify:** Register as `Repo(kind: 'folder')` through an Orca-owned host-aware path. Read back Repo ID, canonical path, host ID, kind, and storage identity. The current `repo.add` and `repo.create` RPCs do not meet this contract; the worker must first deliver the narrow host/identity proof seam or keep creation unsupported.
5. **Publish artifacts:** Re-read and validate the ratified allowlist and artifact pointer against the operation's expected catalog revision immediately before staging. If a non-empty legacy pointer exists, stop artifact publication until its ratified migration/retention procedure has preserved it and defined the initial manifest revision. Otherwise stage immutable files and manifest, verify exact bytes, then CAS the catalog `coordinatorLocation`, complete `coordinatorRef`, artifact manifest pointer, and operation result only if the exact prior pointer still matches. Do not report fully ready if any selected file or reference is missing.
6. **Enroll Run:** Require the user's enrollment/rebind choice and fresh strict server attestation; commit the correlation under a current ticket CAS. Do not chain external adapter effects into this operation.

Filesystem creation, Orca Repo registration, and ticket catalog CAS are independent durability boundaries. A failure after one boundary leaves that state in place and returns `pending` or `recovery-required`, never top-level success and never destructive compensation. Retry rereads all three owners and resumes only when the operation digest, route, directory marker/identity, Repo identity, artifact hashes, and expected ticket revision still match. Changed state requires explicit reconciliation.

### TW-05 implementation gates and acceptance

- **Folder gate:** an Orca-owned API must prove actual host/storage route and stable directory object identity, then return exact `Repo(kind: 'folder')` read-back. The existing host-unaware registration path cannot be used. WSL/SSH/paired paths remain unsupported until their route proof and ticket-host mapping are demonstrated; no fallback is permitted.
- **Artifact gate:** a ticket owner must ratify a document allowlist and writer/size policy. No current source provides the document IDs or user preference. The manifest can be implemented/tested with a synthetic allowlist, but product publication stays unavailable until a real allowlist is approved.
- **Enrollment gate:** Orca must add strict caller attestation and expose the current Run host/binding generation from its own authority. The current methods and `consumer_generation` alone do not satisfy this. Enrollment schema versioning must be compatible with strict v1 readers.
- **Fixtures:** cover path collision across hosts; absent/mismatched owner marker; copied marker at changed storage identity; same path with replaced directory instance; repoId/host/path/kind mismatch; ticket authority or ledger CAS conflict; traversal, symlink/reparse, and unsupported route; strict caller proof missing/mismatched/request-from spoof; stale Run generation; opaque legacy artifact pointer blocks file writes and catalog-pointer replacement; owner-ratified migration preserves the exact legacy value and defines the initial manifest revision; pointer changes during retry conflict; retry after filesystem, Repo registration, manifest publication, catalog commit, and lost acknowledgement; idempotent same-operation retry; explicit rebind conflict; and no overwrite/deletion of user files or prior revisions.
- **Success rule:** each requested operation reports success only after its own outputs have exact positive read-back. Artifact publication requires either no existing pointer or a verified recognized manifest pointer; an unmigrated non-empty legacy pointer leaves artifact setup unavailable and is preserved. A combined folder/artifact/enrollment setup reports ready only when every requested folder identity, selected allowlisted artifact byte and manifest, ticket CAS, and Run correlation is verified. Any unselected/unsupported route, missing document choice, incomplete write, stale Run, or uncertain owner result remains unavailable/pending and preserves existing data.

**DAG:** TW-05 contract work remains independent of TW-05G implementation. TW-04B external effects still wait for TW-05G. This draft does not authorize effects, issue a token, or solve Run-binding exclusion.

## TW-05G — root gateway for ticket effects

### Authority inputs

The candidate action is classified by a closed action registry. The gateway receives the ticket identity, current ledger epoch/revision, exact action and target, prepared-plan identity, confirmation result, and configured adapter execution domain. The trusted caller context is derived inside Orca main from the authenticated runtime route and current orchestration database state.

Admission requires a new strict ticket-specific caller-attestation seam in Orca main. The current `runCreate`/`runUse` caller check is insufficient because it can proceed with absent or unresolved compatibility evidence, falling back to the request `from` handle for pane lookup. The new seam must establish an authenticated live caller; neither a stable pane nor a current Run lookup grants that authority by itself. It must then verify that the attested caller is the current coordinator pane for the Run; the ticket's validated catalog correlation names that same Run and execution host; the ticket authority/epoch/revision and exact target/action still match; and the configured profile permits the requested adapter domain. A worker Run, another pane, external CLI, stale snapshot, fixture, or renderer-supplied identity cannot satisfy this check.

Read-only `plan` output never authorizes an effect. A one-use, expiring, target-bound plan capability is the current design direction, but its issuer, lifetime, encoding, transport, and consumption protocol remain open. The shared task graph's five-minute value is a proposal to ratify, not a frozen wire contract. Whatever form is selected must bind to the exact ticket authority/epoch/revision, operation/action, target and plan, reject replay or changed input, and remain separate from Orca's own mutation receipt.

### Effect and Run-binding exclusion

**INVARIANT:** External ticket effects can begin only through an Orca root gateway after strict server-side caller attestation, admission, and a distinct check immediately before the effect. Current Run APIs do not strictly attest every caller, so ticket enrollment and action admission must fail closed until the new attestation seam exists. That check must compare fresh caller proof, current pane-to-Run binding, catalog Run correlation, current ticket revision, exact action/target, confirmation, and execution-domain authorization. Contact loss or unsupported/mismatched host routing is unavailable; it never falls back to a different local host.

**RECOMMENDATION:** Add a durable in-flight effect exclusion to the existing Orca orchestration authority. Its record should identify the ticket operation/request digest, Run, the then-current binding snapshot, and the adapter execution domain. It must be acquired before the pre-effect check and remain held from that check through a durable terminal ticket receipt and positive evidence that effect-producing processes are quiescent. It is an Orca-owned lifecycle exclusion, not a new ticket-side Run/status store.

While this exclusion is held, every operation that could replace, remove, or invalidate the coordinator Run must serialize against it: at minimum `runCreate`, `runUse`/`bindRun`, `unbindOtherRunsForPane`, `orchestration.reset --all`/`resetAll`, and any later path that deletes or replaces a Run or clears exclusion/recovery rows. `resetAll()` currently deletes every Run, so it must either be refused until active effects are terminal and quiescent or safely reconcile them first. The durable exclusion must survive the reset transaction; reset must not clear its row or erase evidence needed for recovery. Other reset scopes must also be proven not to delete active exclusion or recovery state. A competing change may wait or return a typed in-flight result; it must not commit first and leave a ticket effect running under a former root. The guard belongs at a shared Orca authority seam so callers cannot bypass it by invoking a lower-level bind helper or reset API.

This proposed exclusion is **not present in the inspected APIs**. The current Run transaction ends before the ticket coordinator or adapter effect runs. `consumer_generation` may be captured and compared as one part of the expected current Run snapshot, but it is not the exclusion and cannot release one.

### Partial failure, replay, and recovery

| Failure point                                                                             | Required result                                                                                                                                                                                                                  |
| ----------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Admission mismatch or changed ticket revision                                             | Reject before ticket or adapter effect; report stale/blocked with stable reason.                                                                                                                                                 |
| Ticket operation is admitted but Orca exclusion cannot be durably acquired                | No adapter effect. Return blocked/unavailable and leave the ticket operation recoverable or safely unadmitted.                                                                                                                   |
| Root binding changes before the pre-effect check                                          | Reject before effect. Do not transfer the old admission to a replacement Run.                                                                                                                                                    |
| `orchestration.reset --all` is requested while an exclusion is held or recovery-required  | Block reset or reconcile the exact effect to terminal/quiescent first. Preserve the exclusion and evidence across reset; never delete its durable state with the Run rows.                                                       |
| Another reset or destructive Run lifecycle path clears/replaces identity or recovery rows | Gate it against active exclusions or prove those rows remain durable and reconcilable. Do not release an exclusion as a side effect of reset.                                                                                    |
| Effect completes but ticket acknowledgement is absent or uncertain                        | Keep the Orca exclusion held/recovery-required. Reconcile the exact ticket operation and read-back; do not repeat an ambiguous effect or infer quiescence from contact loss.                                                     |
| Orca, ticket process, or transport restarts during an effect                              | Persist the exclusion across restart. Release only after the exact operation has a durable terminal receipt and positive process/effect-quiescence evidence. Pending, unreachable, or unverifiable evidence keeps the exclusion. |
| Same operation ID and same request is retried                                             | Return/reconcile the existing durable stage result without starting a duplicate effect.                                                                                                                                          |
| Operation ID is reused with a different request/target                                    | Reject as request mismatch before effect.                                                                                                                                                                                        |

Ticket adapter stages, Orca worktree/agent mutations, and external cleanup have separate owners and receipts. A successful Orca receipt does not prove adapter success; an adapter receipt does not prove a worktree mutation. A ticket plan capability is never substituted for an Orca orchestration request ID/receipt.

### Open TW-05G decisions

- **OPEN DECISION:** Where to store the durable exclusion in Orca's orchestration schema and which common lifecycle seam can enforce it for every create/use/bind/unbind and Run deletion/reset path. `reset --all` deletes Run rows; decide how reset is gated or reconciled and how exclusion/recovery state survives the reset transaction and startup recovery.
- **OPEN DECISION:** Define the new strict server-side live-caller attestation seam required for ticket enrollment and effect admission. It must reject missing/unresolved evidence and cannot treat `from`, a stable pane, a current Run, or a caller-declared host as authority.
- **OPEN DECISION:** Define the cross-store ordering between acquiring the Orca exclusion and the ticket ledger's admission CAS. Specify safe outcomes for every crash/ack-loss interleaving; there is no atomic commit across the two stores.
- **OPEN DECISION:** Define the exact terminal-receipt and effect-quiescence evidence required to release after gateway/host restart. A missing process or lost connection is not evidence of quiescence.
- **OPEN DECISION:** Ratify plan-capability issuer, binding fields, TTL, delivery channel, replay storage and one-use consumption semantics. Do not add an endpoint or token format before that decision.
- **OPEN DECISION:** Decide whether gateway recovery uses a future resident no-start transport shared with TW-06T or a separately scoped transport. Snapshot transport must not be assumed to authorize mutations.
- **OPEN DECISION:** Freeze supported root/adapter host-scope mappings for the MVP, including Windows-root-to-WSL-coordinator and Windows-native IIS execution, and the exact fail-closed behavior for unsupported SSH/paired routes.
- **OPEN DECISION:** Define user confirmation ownership and binding to the exact target/plan, and the public failure/recovery reason vocabulary without exposing paths, tokens, or host secrets.

## Contract packets and DAG impact

1. **TW-05 contract packet:** freeze the coordinator directory ownership/identity, initial artifact schema and retention, folder registration/host-proof seam, strict caller-attestation requirement, first enrollment and retry/rebind rules. Then implement only ticket catalog/ledger, directory, artifact and correlation work. Orca continues to own project registration, agent/session, Run creation and Run binding.
2. **TW-05G contract packet:** separately freeze root attestation inputs and implementation seam, action/target-plan binding, confirmation and capability semantics, durable binding exclusion across create/use/bind/unbind/reset/delete, cross-store crash ordering and release evidence. Only after that should the Orca gateway and ticket effect admission be implemented.

The current DAG remains `TW-05 → TW-05G → TW-04B, TW-08`; TW-05G continues to block live external adapter effects and ticket actions. TW-05's artifact/correlation contract remains the prerequisite for M3 coordinator documents. TW-04A fixture work and TW-06T snapshot transport discovery may continue independently. If TW-05G chooses to share a resident transport with TW-06T, the Orchestrator should add that explicit dependency before gateway implementation; snapshot-read completion by itself is not mutation authority.
