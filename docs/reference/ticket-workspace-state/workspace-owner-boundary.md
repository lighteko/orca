# TW-02F / TW-02L — Ticket `WorkspaceRef` to Orca owner boundary

Status: fixture TW-02F owner binding and TW-06F main/preload consumption are implemented and reviewed; authenticated live ingress and TW-02L owner composition remain open.
Scope: one exact local-native Git worktree identity match from a validated fixture; TW-01 Git status capture is a later live composition. This contract does not expose a public `clear` verdict.

See [`ticket-workspace-common-v1.ts`](../../../ticket-workspace/packages/contracts/src/ticket-workspace-common-v1.ts#L106), [`ticket-contract-validator-v1.ts`](../../../ticket-workspace/packages/contracts/src/ticket-contract-validator-v1.ts#L143), and [`worktree-catalog-binding-types.ts`](../../../src/main/persistence/loading-store/worktree-catalog-binding-types.ts#L5).

It returns an internal binding token and target. The status capture then re-attests the binding and subject, creates `observationId` and `ownerReadStartedAt` inside the Orca owner, and checks again after status and marker reads. See [`runtime-worktree-catalog-binding.ts`](../../../src/main/runtime/runtime-worktree-catalog-binding.ts#L58), [`worktree-catalog-binding-types.ts`](../../../src/main/persistence/loading-store/worktree-catalog-binding-types.ts#L13), and [`runtime-git-status-record-capture.ts`](../../../src/main/runtime/runtime-git-status-record-capture.ts#L158).

The injected TW-06P/T producer and client do not provide a production service artifact, authenticated resident endpoint, or live owner composition. ### Pure selection and five-field mapping

This synchronous projection is independently testable with an injected snapshot that has already passed the full ticket-owned validator. It does not authenticate the source, attest an Orca workspace, perform I/O, or authorize live evidence. TW-02F adds a separate asynchronous exact-binding step after this projection.

1. Select exactly one ticket and repository row by `ticketKey` and `repositoryId`; require a present `target` with `kind: 'git-worktree'` and schema version 1.
2. Require `repositoryId === target.repoId`, the exact Orca local execution-host ID, and all five mapping values. Do not require `referenceState: 'matched'`: that value belongs to the ticket producer and is not an Orca claim. A ticket producer may report `unavailable` for a local reference claim or `unsupported` for SSH; Orca produces its own result after it attests the supplied target. Folder, missing, ambiguous, or non-local refs map to unavailable.
3. Return an immutable mapping attempt containing the source `snapshotRevision`, ticket provenance tuple, selected ticket/repository/ref, and the five-field `WorktreeCatalogBindingRequest`. Do not include a path, Orca binding token, observation ID, or owner timestamp.

### Fixture exact binding and navigation

The bounded TW-02F allocation accepts only an injected fixture snapshot that main has parsed with `parseTicketNavigatorSnapshotUtf8V1` or validated with `validateTicketNavigatorSnapshotV1`. It runs the pure mapper, then `RuntimeWorktreeCatalogBindingCommands.resolveExactLocalNativeGitTarget` and produces a separate `matched` / `unavailable` result tied to the input `snapshotRevision`, `ticketKey`, and `repositoryId`. A match proves only the Orca catalog/native target at that read. Keep catalog tokens, registration evidence and ticket target data in main; expose no path or ticket-provided target through TW-06F's renderer presentation DTO. For navigation, the renderer sends only `{ snapshotRevision, ticketKey, repositoryId }`; TW-06F's main-owned accessor reloads its own canonically validated active fixture and checks the revision before TW-02F rebinds. The request never accepts a renderer snapshot, ref or worktree ID. Only then may main return the freshly attested existing Orca-owned worktree ID to the established `activateAndRevealWorkspace` path. That ID encodes a path under Orca's current ID scheme, so it is never taken directly from ticket input. TW-07F wires the final click request serially after both workstreams. A changed Orca binding or revision is stale for this fixture match; historical fixture `generatedAt`/`staleAfter` values are not compared to Orca wall time or promoted to live currentness.

The approved `snapshot.full` fixture is a positive presentation case but a negative owner-match case: its workspace `repositoryId` is `common-api` while `target.repoId` is `repo-1`. TW-02F rejects that relation and supplies a separate Orca-owned positive integration vector with a recomputed canonical digest. The seven approved public files remain byte-exact.

### Historical live owner sketch; production eligibility still gated

The sequence below predates the reviewed P4/P5 same-catalog-read eligibility rule. It is not an implementation packet: TW-02L must also prove target eligibility from a fresh read on one authenticated lease, apply P5 whole-snapshot support, and use one outer deadline across source reads, binding and capture. See [the current DAG](./task-graph.md#tw-02l--compose-authenticated-live-ticket-to-orca-owner-evidence) and [transport policy](./resident-ticket-transport.md#proposed-source-high-water-projection-eligibility-and-clocks).

An injected fixture supports pure mapping and Orca exact-target tests, but never establishes ticket source currentness or live evidence. A live invocation must obtain its starting snapshot through an authenticated current-source callback bound to the configured authority/profile; a caller-provided snapshot alone is not live authority.

1. Obtain the starting snapshot through the authenticated current-source callback bound to the configured authority/profile. Run the complete ticket-owned semantic validator on its bounded response. Use the delivered narrow exports `parseTicketNavigatorSnapshotUtf8V1` / `validateTicketNavigatorSnapshotV1` (including strict shape checks, snapshot digest, duplicate ticket/repository checks, and byte limits); JSON Schema validation alone is insufficient. Do not launch WSL or the ticket CLI for a read.
2. Freeze the validated snapshot and run the pure selector/mapper. Use the resulting five-field request with Orca's async exact binder, which revalidates Orca catalog incarnation/revision, host, instance, identity, route, registration, and target. The ticket producer's `referenceState` is not the match result.
3. Recheck the authenticated current-source callback after asynchronous target attestation. Validate that response with the same ticket-owned semantic validator and compare its profile, authority ID, ledger epoch/revision, projection sequence, catalog digest, selected ticket/repository ID, and exact ref with the frozen input. A new bound catalog read may regenerate `generatedAt`/`staleAfter` and therefore `snapshotRevision` without changing those source facts. If the source facts match and Orca attestation succeeded, Orca produces a separate `matched` result tied to the original snapshot's `snapshotRevision`; otherwise produce `unavailable`. Never mutate the ticket snapshot or set its `referenceState` to `matched`. Keep the binding token internal.
4. For Git evidence, run the existing owner capture and recheck the authenticated current-source callback again after asynchronous capture. Validate and compare the same source facts and exact ref; discard evidence if they changed or if Orca's binding/route/registration revalidation fails. Never reuse an earlier observation for the same path.
5. Keep match and evidence availability distinct. A matched workspace does not prove a complete Git read; an unavailable capture does not erase a valid match. Do not project an empty status as public `clear`; completeness and cross-owner aggregation remain separate gates.

**Clock rule:** Ticket snapshot timestamps and Orca's owner clock are different authorities. Do not compare `generatedAt`/`staleAfter` to Orca wall time or treat receipt time as freshness. The authenticated source callback must prove that each response is current for that request; post-attestation and post-capture checks must match the frozen source tuple and selected ref, while the separate Orca result remains tied to the original `snapshotRevision`. The protocol that proves request freshness across the resident boundary is not defined yet, so production live admission remains gated. Orca's same-owner `ownerReadStartedAt` and monotonic deadline remain the only freshness basis for the Git capture itself.

## Reuse proposal and open decisions

**DECISION — Use `TicketNavigatorSnapshotV1` as the ticket-side input to the fixture projection-to-binding join in Orca main.** The delivered narrow archive carries the provenance tuple, ticket/repository identity, canonical `WorkspaceRef`, full semantic validator and fixture corpus. Orca's binding request remains an internal runtime type, not a cross-process contract. TW-06F separately owns a targetless, action-free Orca renderer presentation result; it must project from the validated canonical snapshot because the approved fixture-envelope validator returns status/provenance only. Live transport framing remains a later decision and must not restate ticket-owned fields or become a second schema owner.

**FACT — The fixture and live joins must enforce** `repositoryId === workspaceRef.repoId` / `target.repoId`. **OPEN — Contract-owner policy:** decide separately whether this mismatch rejects an entire catalog/navigator DTO or only makes the selected mapping unavailable. The first bounded implementation enforces equality in the pure join and tests both match and mismatch; it does not change canonical catalog/snapshot admission or approved fixtures.

**FACT — Package and fixture consumption (TW-00C/TW-06F).** The user-approved narrow contract archive is installed through Orca's local `file:` devDependency and passed public PR CI with no private-submodule fetch. It exports the browser-safe full snapshot semantic validator; actual Orca main and sandboxed-preload fixture consumption passed TW-06F review. Do not import lifecycle source from the private submodule or copy a second schema into Orca.

**OPEN — Authenticated transport and freshness.** TW-06P owns producer projection/currentness; TW-06T owns authority/profile binding, no-start connection lifecycle, and authenticated delivery. Together they must prove request/source freshness and cross-process clock admission. A new local IPC contract could carry bytes inside Orca, but it does not solve ticket-process ingress or freshness and must not restate ticket-owned fields. These are gates for production live admission, not for pure mapping design.

**DECISION — The completed Orca TW-02F packet owns pure mapping plus fixture exact binding and click-time rebinding.** It accepts an injected, already validated snapshot and keeps all target attestation in Orca main. It does not claim live ticket currentness, perform TW-01 Git capture, or provide a production evidence provider. No TW-06T transport is needed for fixture tests. TW-02L later composes authenticated live source checks and TW-01 capture.
