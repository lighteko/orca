# TW-02 — Ticket `WorkspaceRef` to Orca owner boundary

Status: decision-ready field contract; narrow contract package is locally delivered, while owner ingress, actual main/preload use and live transport remain open.
Scope: one exact local-native Git worktree capture. This contract does not expose a public `clear` verdict.

## Confirmed facts

- **FACT — Ticket owns the source contract.** The pinned ticket source is a separate private workspace. Its contracts package exports the strict catalog, navigator snapshot, `WorkspaceRefV1`, fixture corpus, and generated JSON Schema artifact. Its README says Orca consumes released protocol artifacts and must not import ticket lifecycle implementation. See [`ticket-workspace-common-v1.ts`](../../../ticket-workspace/packages/contracts/src/ticket-workspace-common-v1.ts#L106), [`ticket-navigator-snapshot-v1.ts`](../../../ticket-workspace/packages/contracts/src/ticket-navigator-snapshot-v1.ts#L76), [`ticket-contract-artifact-v1.ts`](../../../ticket-workspace/packages/contracts/src/ticket-contract-artifact-v1.ts#L15), [`packages/contracts/package.json`](../../../ticket-workspace/packages/contracts/package.json#L10), and [`ticket-workspace/README.md`](../../../ticket-workspace/README.md#L5).
- **FACT — Existing snapshot has the required ticket-side fields.** `TicketNavigatorSnapshotV1.source` contains `authorityId`, `ledgerEpoch`, `ledgerRevision`, `projectionSequence`, and `catalogDigest`; each ticket has `ticketKey`; each workspace has `repositoryId` and optional `target: WorkspaceRefV1`. The snapshot is strict, digest-validated, and capped at 2 MiB UTF-8 by the ticket validator. See [`ticket-navigator-snapshot-v1.ts`](../../../ticket-workspace/packages/contracts/src/ticket-navigator-snapshot-v1.ts#L47) and [`ticket-contract-validator-v1.ts`](../../../ticket-workspace/packages/contracts/src/ticket-contract-validator-v1.ts#L207).
- **FACT — `git-worktree` maps exactly to Orca's five request fields.** Ticket `WorkspaceRefV1` has `executionHostId`, `identityKey`, `instanceId`, `worktreeId`, and `repoId`; Orca's `WorktreeCatalogBindingRequest` has `executionHostId`, `identityKey`, `instanceId`, `worktreeId`, and `repositoryId`. `repoId` must equal the ticket repository record's `repositoryId` before mapping. Ticket validation enforces unique ticket and repository IDs, but does not enforce that cross-field equality. See [`ticket-workspace-common-v1.ts`](../../../ticket-workspace/packages/contracts/src/ticket-workspace-common-v1.ts#L106), [`ticket-contract-validator-v1.ts`](../../../ticket-workspace/packages/contracts/src/ticket-contract-validator-v1.ts#L143), and [`worktree-catalog-binding-types.ts`](../../../src/main/persistence/loading-store/worktree-catalog-binding-types.ts#L5).
- **FACT — Orca already owns exact runtime binding and freshness.** Its binder admits only the local execution host, resolves the current repo/worktree catalog row, checks instance and identity, reads the native Git registration before and after, and revalidates the catalog incarnation/revision. It returns an internal binding token and target. The status capture then re-attests the binding and subject, creates `observationId` and `ownerReadStartedAt` inside the Orca owner, and checks again after status and marker reads. See [`runtime-worktree-catalog-binding.ts`](../../../src/main/runtime/runtime-worktree-catalog-binding.ts#L58), [`worktree-catalog-binding-types.ts`](../../../src/main/persistence/loading-store/worktree-catalog-binding-types.ts#L13), and [`runtime-git-status-record-capture.ts`](../../../src/main/runtime/runtime-git-status-record-capture.ts#L158).
- **FACT — The cross-repository ingress is not implemented.** Orca's root pnpm workspace contains native Windows packages, not the ticket submodule; its approved narrow snapshot contract is installed through a local `file:` devDependency, but no TW-02 owner adapter or actual main/preload consumer exists. TW-06T records that the strict ticket snapshot has no production producer, authenticated resident endpoint, or lifecycle yet. See [`pnpm-workspace.yaml`](../../../pnpm-workspace.yaml#L10), [`project-state.md`](./project-state.md#L61), and [`task-graph.md`](./task-graph.md#L156).

### Pure selection and five-field mapping

This synchronous projection is independently testable with an injected snapshot that has already passed the full ticket-owned validator. It does not authenticate the source, attest an Orca workspace, perform I/O, or authorize live evidence.

1. Select exactly one ticket and repository row by `ticketKey` and `repositoryId`; require a present `target` with `kind: 'git-worktree'` and schema version 1.
2. Require `repositoryId === target.repoId`, the exact Orca local execution-host ID, and all five mapping values. Do not require `referenceState: 'matched'`: that value belongs to the ticket producer and is not an Orca claim. A ticket producer may report `unavailable` for a local reference claim or `unsupported` for SSH; Orca produces its own result after it attests the supplied target. Folder, missing, ambiguous, or non-local refs map to unavailable.
3. Return an immutable mapping attempt containing the source `snapshotRevision`, ticket provenance tuple, selected ticket/repository/ref, and the five-field `WorktreeCatalogBindingRequest`. Do not include a path, Orca binding token, observation ID, or owner timestamp.

### Live owner orchestration and result

Injected snapshots support pure mapping tests only. A live invocation must obtain its starting snapshot through an authenticated current-source callback bound to the configured authority/profile; a caller-provided snapshot alone is not live authority.

1. Obtain the starting snapshot through the authenticated current-source callback bound to the configured authority/profile. Run the complete ticket-owned semantic validator on its bounded response. Use `validateTicketContractV1` (including strict shape checks, snapshot digest, duplicate ticket/repository checks, and byte limits); JSON Schema validation alone is insufficient. Do not launch WSL or the ticket CLI for a read.
2. Freeze the validated snapshot and run the pure selector/mapper. Use the resulting five-field request with Orca's async exact binder, which revalidates Orca catalog incarnation/revision, host, instance, identity, route, registration, and target. The ticket producer's `referenceState` is not the match result.
3. Recheck the authenticated current-source callback after asynchronous target attestation. Validate that response with the same ticket-owned semantic validator and compare its profile, authority ID, ledger epoch/revision, projection sequence, catalog digest, selected ticket/repository ID, and exact ref with the frozen input. A new bound catalog read may regenerate `generatedAt`/`staleAfter` and therefore `snapshotRevision` without changing those source facts. If the source facts match and Orca attestation succeeded, Orca produces a separate `matched` result tied to the original snapshot's `snapshotRevision`; otherwise produce `unavailable`. Never mutate the ticket snapshot or set its `referenceState` to `matched`. Keep the binding token internal.
4. For Git evidence, run the existing owner capture and recheck the authenticated current-source callback again after asynchronous capture. Validate and compare the same source facts and exact ref; discard evidence if they changed or if Orca's binding/route/registration revalidation fails. Never reuse an earlier observation for the same path.
5. Keep match and evidence availability distinct. A matched workspace does not prove a complete Git read; an unavailable capture does not erase a valid match. Do not project an empty status as public `clear`; completeness and cross-owner aggregation remain separate gates.

**Clock rule:** Ticket snapshot timestamps and Orca's owner clock are different authorities. Do not compare `generatedAt`/`staleAfter` to Orca wall time or treat receipt time as freshness. The authenticated source callback must prove that each response is current for that request; post-attestation and post-capture checks must match the frozen source tuple and selected ref, while the separate Orca result remains tied to the original `snapshotRevision`. The protocol that proves request freshness across the resident boundary is not defined yet, so production live admission remains gated. Orca's same-owner `ownerReadStartedAt` and monotonic deadline remain the only freshness basis for the Git capture itself.

## Reuse proposal and open decisions

**RECOMMENDATION — Prefer `TicketNavigatorSnapshotV1` as the ticket-side input to a pure projection-to-binding join in Orca main.** The existing snapshot carries the provenance tuple, ticket/repository identity, and canonical `WorkspaceRef`; the artifact and fixture corpus provide a versioned validation source. Orca's current binding request is an internal runtime type, not a cross-process contract. This reuse proposal is not frozen until package delivery and transport are reviewed. A new IPC/service contract remains an option for transport framing, but should not restate ticket-owned fields or become a second schema owner.

**FACT — The live join must enforce** `repositoryId === workspaceRef.repoId` / `target.repoId`. **OPEN — Contract-owner policy:** decide separately whether this mismatch rejects an entire catalog/navigator DTO or only makes the selected mapping unavailable. The first bounded implementation should enforce equality in the pure join and test both match and mismatch; it must not change canonical catalog/snapshot admission or fixtures without that separate decision.

**OPEN — Package delivery (TW-00C).** The ticket root is `private: true`, lives in the pinned submodule, and is outside Orca's pnpm graph. The contracts package exports a built module and JSON Schema artifact, but Orca does not consume either today; the artifact alone omits semantic checks and the current validator imports Node APIs that are unavailable in sandboxed preload. TW-00C must deliver a source-pinned full runtime contract that works in Orca main and preload. A public vendored copy also needs a distribution decision. Do not add a relative import into the submodule or silently copy the schema into Orca.

**OPEN — Authenticated transport and freshness.** TW-06P owns producer projection/currentness; TW-06T owns authority/profile binding, no-start connection lifecycle, and authenticated delivery. Together they must prove request/source freshness and cross-process clock admission. A new local IPC contract could carry bytes inside Orca, but it does not solve ticket-process ingress or freshness and must not restate ticket-owned fields. These are gates for production live admission, not for pure mapping design.

**ASSUMPTION — The first Orca implementation packet owns only a pure projection-to-binding adapter that accepts an injected, already validated snapshot.** Its design can be reviewed before resident ingress; typed implementation and tests in Orca wait for TW-00C's canonical contract delivery. No TW-06T transport is needed for its pure tests. This does not assert that a live source, transport, clock handoff, or production ticket evidence provider exists.

## Smallest implementation packet after the open decisions

1. **Pure mapping owner after TW-00C:** add a small selector/five-field mapping module and focused tests using the delivered canonical ticket type/validator. Accept an injected validated snapshot; enforce unique selection, `repositoryId === target.repoId`, local git-worktree kind, and the exact five-field mapping. Cover producer `referenceState` values `unavailable`/`unsupported`, folder/missing/non-local refs, duplicate/mismatch rejection, and no path-derived identity. This pure task needs no current-source callback, binder, capture, or resident ingress.
2. **Orca live owner:** separately compose the authenticated current-source callback with the pure mapper, async exact binder, owner capture, and pre/post source tuple checks. Produce a separate Orca-owned match result tied to `snapshotRevision`; keep the binding token internal and prove caller data cannot set observation ID/read-start time. This live task waits on package delivery and TW-06T freshness/transport review.
3. **Separate contract-owner decision:** decide whether repository/ref mismatch should reject the whole canonical catalog/navigator DTO. If yes, assign the ticket contract owner the validator, corpus, tests, artifact regeneration, and publication changes. If no, keep the stricter relation at the live join only.
4. **Transport owner (TW-06T):** separately provide the authenticated current-snapshot ingress and its request freshness proof. No preload/renderer work is part of the pure mapping packet. Production live admission depends on this transport and its cross-process clock contract; the mapping tests do not.

## DAG impact

The reviewed DAG now adds TW-00C before Orca TW-02 implementation. TW-02 pure mapping remains independent of TW-06T and TW-05. Production live admission additionally waits for TW-06P/TW-06T source-currentness and transport decisions.
