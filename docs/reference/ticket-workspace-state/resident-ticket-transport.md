## Version 1 logical protocol

The wire protocol is named `ticket.navigator.resident` and has an independent semantic version, separate from the Orca runtime protocol and ticket package version. Version 1 has a strict handshake, a read-only snapshot request, a bounded byte response, cancellation, and typed failure. The endpoint may use any transport later selected by its owners; this contract does not select TCP, named pipes, stdio, HTTP, or a relay.

### Setup and authentication

1. A separate, explicit setup/enable action creates or attaches the resident producer, provisions its authentication material, and returns an **in-memory** authenticated connection lease to Orca main. Only that action may launch WSL or the producer. Setup must identify its target from configured Orca execution-host/profile data, not from renderer-supplied paths.
2. The lease is bound to one Orca installation/session incarnation and exactly one configured tuple: ticket profile `(profileId, schemaVersion, profileVersion)`, expected ticket `authorityId`, and coordinator execution host `(machineId, kind: wsl, distro)`. `stateRoot`, ledger path, endpoint path, and credential reference are not protocol identity fields and are not sent to the renderer.
3. The hello authenticates both peers and negotiates a common protocol version and the required `snapshot.read.v1` plus `no-start.v1` capabilities. `no-start.v1` means the service-side read does not start WSL, a CLI, a shell, coordinator, or child process. Nonces correlate/authenticate a connection and prevent hello replay; they do not prove that a catalog read is fresh. A path, loopback address, PID, endpoint file, `catalogDigest`, or `snapshotRevision` alone is not authentication or source freshness.
4. The authenticated service reports its producer identity/version, profile tuple, authority ID, current ledger epoch, coordinator host identity, connection incarnation, and negotiated capabilities. Orca compares these with its configured/explicitly bound values before marking the lease readable. Missing proof, a mismatch, a version gap, an unsupported profile, or a missing capability leaves it unavailable.
5. Authentication material is setup-owned, scoped to this profile/authority, revocable/rotatable, and never placed in argv, renderer IPC, snapshot JSON, ordinary logs, or diagnostics. The exact secret storage and handoff mechanism remains open until endpoint technology is selected.

The authenticated session establishes who answered. Request IDs bind response bytes to one request. Neither session nonces, request IDs, nor snapshot digests prove that the producer observed the current catalog for that request. Freshness requires the bound source read and tuple rules below.

## Minimum source-side projection proposal

The first production producer should perform exactly one fresh, authority-bound `TicketWorkspaceCatalogReaderV1.read(capability)` for each `snapshot.read.v1` request and project from that exact validated catalog value. Reusing a prior catalog/snapshot for a new request is not permitted. An equivalent source-owned observation proof is acceptable only if it proves the same current authority/profile/epoch/revision and canonical bytes of the validated catalog value; the current reader returns a parsed catalog, not original raw file bytes. It should not call `status` or any CLI as a subprocess per read, start a coordinator, query provider APIs, or inspect Orca state. A failed/untrusted catalog read yields a typed unavailable response, never an empty catalog snapshot.

- Copy the ticket key, title/label, lifecycle, orchestration correlation, repository ID, display name, `actualRole`, actual state, branch, and ticket-owned `WorkspaceRef` claims from that catalog. Set snapshot workspace `role` from catalog `actualRole`; `desiredRole` is a transition goal and must not be presented as current. A pending role transition remains separately visible only through a later reviewed DTO; it grants no action authority. Enforce the existing unique ticket/repository identities and strict DTO bounds.
- For a supported local-only projection, `availability: 'available'` means the catalog row is displayable; it does not assert Orca workspace readiness or effect authority. The exact logical-v1 host classification below supersedes the earlier SSH-prefix candidate: separate setup-bound ticket-ID allowlists classify every orchestration and present-ref ID before target suppression. A nonmember makes the ticket `unsupported`; an unsuppressed nonmember workspace ref is omitted and has `referenceState: 'unsupported'`. Local claims stay `unavailable` until Orca proves its exact owner join. Fixture `mutationAllowed` never grants live effect authority.
- Until TW-02's exact owner mapping is implemented, use `referenceState: 'unavailable'` for local workspace targets. A target is a ticket claim; only Orca's owner resolver can prove `matched`. A ticket `coordinatorRef` is not proof of an Orca Run or pane binding.
- Use `enrichment: { issue: 'unknown', mergeRequests: 'unknown' }` and empty action arrays in the minimal read-only producer. It introduces no provider query or action authority. Later action descriptors remain presentation hints and must be frozen by TW-06.
- Copy `authorityId`, `ledgerEpoch`, and `ledgerRevision` from the validated catalog. Compute `catalogDigest` as the digest of its canonical bytes. Under the trusted ledger CAS writer, a fixed `(authorityId, ledgerEpoch, ledgerRevision)` has one canonical catalog digest; a previously observed different digest at that same tuple is equivocation and returns unavailable. For this catalog-only projection, keep `projectionSequence: 0`: ledger revision plus catalog digest determines catalog-derived ticket/workspace fields under fixed v1 projection rules. Producer version metadata and observation times may change independently and therefore change `snapshotRevision`. Adding a dynamic source requires a new producer-owned monotonic sequence contract first.
- `generatedAt` is the UTC time immediately after the fresh bound catalog read; `staleAfter` is `generatedAt` plus the fixed TTL. Repeated reads of an unchanged source tuple may regenerate those two observation times without changing `projectionSequence`; `snapshotRevision` then changes because it is the canonical digest of the full snapshot. The response still represents a fresh read, not a cached snapshot. TTL and acceptable WSL-to-Windows clock handoff remain explicit decisions below.
- After projection, run the full runtime contract validator and measure the canonical UTF-8 snapshot. If an otherwise valid catalog projects to more than 2 MiB, return typed unavailable with no partial snapshot. The catalog's larger input limit does not relax the navigator snapshot cap.

This conservative starting shape can display supported ticket catalog entries while keeping local Orca references unavailable until the separate owner join is proven. SSH entries remain visibly unsupported. It does not expose a public `clear` verdict or authorize an action.

### Source freshness and TW-02 currentness handoff

The producer's fresh read and tuple rules, not its nonce or request ID, establish source freshness. A valid authenticated server must bind each response to the exact catalog returned by that request's validated catalog read. For a repeated `(authorityId, ledgerEpoch, ledgerRevision, projectionSequence)`, a different `catalogDigest` is equivocation and unavailable. A same-tuple response may have new `generatedAt`/`staleAfter` values only when it was generated from a new bound read; those metadata changes intentionally produce a different `snapshotRevision`.

`snapshotRevision` is the digest of the complete serialized snapshot, including those observation timestamps. It is not a stable owner-version token across separate fresh reads. **Cross-draft recommendation for TW-02:** after binder/capture, compare profile, authority, epoch, ledger revision, projection sequence, catalog digest, and the exact relevant `WorkspaceRefV1` plus repository ID/owner tuple. Do not require a new producer read to have the same `snapshotRevision`; that would conflict with fresh per-request observations. Keep `snapshotRevision` for validating one exact snapshot and for binding the separate Orca overlay below. TW-02's owner binding remains the authority for whether the reference matched.

### Read and response

Logical request:

```text
snapshot.read.v1 {
  requestId,
  profile: { profileId, schemaVersion: 1, profileVersion },
  authorityId,
  ledgerEpoch,
  deadlineBudgetMs
}
```

The request is accepted only on the current authenticated lease and only when profile, authority, and epoch equal the lease's explicit binding. On first setup, the binding must be established by that explicit setup handshake; a snapshot response cannot silently rebind an existing cache partition. A changed ledger epoch returns `authority_rebind_required`. Rebinding is a separate explicit decision and invalidates current status for the prior binding.

The ticket producer returns the exact UTF-8 JSON bytes of one `TicketNavigatorSnapshotV1`. The source authority, profile, and epoch in the payload must equal the authenticated request/session. The producer derives `ledgerRevision`, `projectionSequence`, `catalogDigest`, `generatedAt`, and `staleAfter` from the source observation; it must not refresh timestamps on Orca receipt or reuse an older snapshot as current. Orca rejects decreasing `(ledgerRevision, projectionSequence)` under the source corpus ordering rule. The producer does not claim an Orca `WorkspaceRef` owner match; TW-02's exact join and `repoId` equality check remain separate.

The transport frames a response as one request-correlated start, one or more byte chunks, and one terminal completion carrying the total byte count. The specific byte framing is an implementation decision, but chunk boundaries must not affect the JSON bytes or UTF-8 decode. The consumer:

- requires the start to carry the request ID and a declared byte length no greater than the cap; the terminal completion repeats the request ID and exact received byte count;
- checks each incoming chunk incrementally and cancels immediately if accumulated snapshot bytes would exceed **2,097,152**; it does not buffer an unbounded body and measure afterward;
- rejects an announced length above the same limit before accepting chunks, while still enforcing the running count because a length claim is untrusted;
- requires one matching completion and an exact final byte count; a close, cancellation, duplicate completion, wrong `requestId`, short body, or trailing bytes observed before candidate admission rejects the whole candidate. A later byte/frame is a lease violation handled by the post-admission rule below, not a retroactive candidate rejection;
- performs fatal UTF-8 decoding once the bounded byte sequence is complete, then strict JSON/schema validation and digest verification; malformed UTF-8, JSON, schema, provenance, or digest never reaches preload;
- keeps framing/control metadata separately bounded and does not count it as snapshot JSON. V1 metadata and error reason codes are strict and small; free-form diagnostics are not carried in the response.

No partial payload replaces the current snapshot. The schema's per-field/array/aggregate limits still apply after the transport byte cap.

### Cancellation and deadline

Each read has one Orca-main-owned monotonic deadline established before transport work starts; endpoint lookup, automatic reconnect, WSL command execution, and CLI launch are forbidden in this path. Send only the remaining budget to the producer; neither peer can extend it. A cancellation or deadline sends `cancel(requestId)` when negotiated. The producer should stop projection/serialization/read work and acknowledge settlement. If settlement cannot be established, Orca retires that connection lease, discards late frames by request/connection incarnation, and does not admit a second read on the ambiguous stream. Cancellation of a read does not stop the resident service, terminals, coordinator, or ticket resources.

**Proposed initial bound for TW-06T to ratify:** 10 seconds end-to-end for a resident snapshot read, with a shorter separately bounded hello during explicit setup. The exact number must be covered by a measured slow/2 MiB stream test before implementation is declared done. The deadline contract is mandatory even if the value changes.

### No-start proof and failure results

`readSnapshot()` is available only through an already-established in-memory lease carrying an authenticated connection incarnation and negotiated `no-start.v1` capability. If the lease is absent, stale, unauthenticated, mismatched, or disconnected, return transport-unavailable immediately. The capability is a negotiated service contract, not by itself proof about Orca main's call graph: implementation proof requires the read method to take only the existing lease and a no-launch request port, plus tests that assert no process/WSL/CLI start calls on connected, disconnected, retry, and cancellation paths. The producer read likewise has no child-process or coordinator-start path. It must not call a generic `ensure*`, process launcher, `runProcess`/`spawnProcess`, `wsl.exe`, shell, CLI `status`, or endpoint startup/probe that can create a resident process. It must not silently answer from Windows/native catalog files or another configured profile. A future reconnect path is setup/lifecycle work and must have its own explicit authority; read retry alone cannot reconnect.

All of these reject the candidate and produce unavailable/stale presentation through TW-06: no lease, no no-start capability, auth failure, no common protocol/capability, wrong profile/authority/host/epoch, revision regression, oversized body, malformed UTF-8/JSON/schema/digest, partial stream, cancellation, timeout, or disconnect. Errors carry stable bounded reason codes only. An old last-verified result may be presented stale by TW-06's separately frozen cache contract, partitioned by execution-host identity, the full profile tuple, authority and ledger epoch; rebind and service/profile updates need explicit invalidation. It never becomes current because contact returned or a digest matched, and any old Orca match overlay is dropped rather than treated as live. Decide whether equivocation or authentication failure quarantines even historical stale display. Transport loss says nothing about remote process exit. If SSH is added in a later scope, contact loss remains `unverifiable` under the SSH boundary.

### Mixed versions

- Negotiate the highest mutually supported semantic protocol version and required capabilities in hello. Never infer support from the ticket package's version string alone.
- Version 1 requires `TicketNavigatorSnapshotV1` contract/schema version 1. Unknown major versions, fields, message kinds, or capabilities fail closed; no fallback to the one-shot status CLI or a weaker transport.
- Keep v1 envelope shapes strict. Any new field, new message kind, or changed meaning needs a new protocol/schema version or an explicitly negotiated capability with a safe older-peer fallback. Do not ship an unnegotiated stream opcode on an Orca paired wire.
- A newer producer may serve v1 only when it can emit the exact v1 projection and semantics. If it cannot, return a version/capability failure. An older consumer must never accept new content merely because it is valid JSON.
- `producer.version` is informational and checked against a TW-06-supported compatibility policy. The package-version range/policy is still a decision; wire capability/schema version is authoritative.

### Privacy and ownership exclusions

- Never serialize `stateRoot`, ledger/checkout paths outside fields already allowed by the ticket DTO, endpoint locator, auth material, command line, stderr, raw validation issues, cache internals, Orca binding tokens, Run/pane evidence, TW-01 observation IDs/timestamps, or agent-status records into protocol diagnostics or preload data.
- Do not log complete snapshots or tokens. Logs may contain connection incarnation hashes only if redacted and bounded, stable reason codes, byte counts, negotiated protocol, and non-secret profile/authority IDs under the existing redaction policy.
- Preserve existing `WorkspaceRefV1` fields as ticket-owned claims; only an Orca owner resolver may attest them. `snapshotRevision`/`catalogDigest` can detect mismatch or regression but cannot authorize actions or replace authentication.
- The producer publishes ticket-owned projection only. Agent/session state remains in Orca's existing execution-host-owned status store. No ticket status store, message bus, liveness vocabulary, or mutation authority is added.

## TW-06 main/preload handoff

TW-06 starts after the producer and transport packets plus their shared protocol are frozen. Its main-side port should consume only `readSnapshot(lease, signal, deadline)` and a bounded byte stream plus private authenticated peer evidence. TW-06 main owns strict snapshot validation, current/stale/unavailable projection, cache partition/rebind behavior, and outgoing wire provenance. Main and preload must run the same full ticket-owned runtime semantic validator, not JSON Schema alone: strict DTO/field bounds, unique ticket and repository IDs, SSH presentation rules, canonical UTF-8 size, and canonical `snapshotRevision` digest equality. ### Earlier v1 stream framing and message table (historical)

The logical transport is one ordered, full-duplex byte stream. This earlier message table records the candidate message flow; the logical-v1 section below supplies its exact strict schemas and supersedes this paragraph's original unprotected frame candidate. Hello frames have a four-byte unsigned big-endian canonical JSON body and no trailer. Every post-finish frame has the same prefix and body **plus a raw 32-byte directional HMAC trailer**. Control bodies are at most 4,096 bytes and `snapshot.chunk` bodies at most 24,576 bytes. Real endpoint and credential provenance remain production gates.

This historical table's field summaries and capability ordering are not normative; use the strict union and exact ordered capabilities in Logical v1 below. Request IDs remain non-repeating 128-bit random values within a process/session; a duplicate closes the lease without an error frame.

| Direction | Frame | Required content |
| --- | --- | --- |
| client → service | `clientHello` | `protocolVersion: 1`, session ID, client nonce, exact profile/authority/host/artifact binding, required capabilities `snapshot.read.v1`, `no-start.v1`, `source.bind.v1`, and client proof. |
| service → client | `serverHello` | echoed client nonce, fresh service nonce, connection incarnation, exact binding tuple, service release ID and artifact digest, accepted protocol/capabilities, and server proof. This is a challenge; no lease is readable yet. |
| client → service | `clientFinish` | server-provided `connectionIncarnation` plus `clientFinishProof` over the full hello transcript including the fresh server nonce and server proof. The service grants a lease only after verifying it for this live, unexpired challenge. |
| client → service | `source.bind` | setup-only request ID plus profile and expected authority; no renderer caller can issue it. |
| service → client | `source.bound` or `error` | matching request ID, `authorityId` and `ledgerEpoch`, or a stable bounded error code. `source.bound` is a validated fresh read, not an authorization result, and does not seed/advance high-water. |
| client → service | `snapshot.read` | unique request ID, exact bound profile/authority/epoch and `deadlineBudgetMs` no greater than 10,000. |
| service → client | `snapshot.begin` | request ID and `snapshotBytes` in `1..2,097,152`. Sent only after the whole canonical snapshot is validated and bounded. |
| service → client | `snapshot.chunk` | request ID, zero-based contiguous index, canonical unpadded base64url of at most 16,384 decoded bytes. There are at most 128 chunks; all but the last are exactly 16,384 bytes. |
| service → client | `snapshot.end` | request ID, exact byte count and chunk count. Exactly one matching terminal follows a successful begin. |
| client → service | `cancel` | the one in-flight request ID. It never stops the resident service or coordinator. |
| service → client | `cancelled` or `error` | request-correlated terminal only after work is settled; stable bounded reason code, no free-form diagnostics. |

The receiver checks the prefix before allocating a frame, enforces running frame/body/chunk totals, base64url canonicality, request ID and sequence, fatal UTF-8 decoding, exact length and one terminal. It concatenates no more than 2,097,152 snapshot bytes, parses the snapshot, runs the full ticket-owned semantic validator/digest check, reserializes the parsed value with the ticket-owned canonical serializer, and requires byte-for-byte equality with the received payload before admission/high-water update. This rejects valid-but-noncanonical JSON (including alternate whitespace/key order) instead of treating canonical digest equality as canonical wire bytes. The producer applies the same parse → validate → canonical-reserialize equality check before `snapshot.begin`; this matches the existing fixture service's boundary ([`ticket-workspace-fixture-service.ts`](../../../src/main/ticket-workspace/ticket-workspace-fixture-service.ts#L90)). Partial bytes never replace a prior verified value. An oversized projected snapshot returns `error(snapshot_too_large)` before `snapshot.begin`; an untrusted declared or actual over-limit body cancels and retires the lease.

**Finite admission barrier:** inbound bytes are processed by one serialized stream pump. On a successful read, the matching `snapshot.end` **including its verified 32-byte trailer** completes a candidate but does not itself publish it. The pump parses the remainder of the same delivered byte batch; any complete frame or partial byte after that trailer observed before admission rejects the candidate without publishing or advancing high-water. After that batch is drained, the receiver performs the final checks and, within the read deadline, atomically commits the permitted durable high-water update and publishes the admitted snapshot before processing a later delivery. This barrier does not wait for EOF or a quiet period. Any unexpected byte/frame delivered after admission retires the lease and revokes live current plus its matched overlay; it does not retroactively reject the admitted response or roll back its valid durable high-water. Control text, stderr, diagnostics and framing overhead do not count as snapshot JSON but remain separately bounded.

**Proposed timing bounds:** 5,000 ms for explicit-setup hello/source bind and 10,000 ms end-to-end for a snapshot read, measured by Orca main from before transport work on a monotonic clock. The producer receives only the remaining read budget. **OPEN:** ratify the values after a measured 2 MiB stream. Cancellation must settle before the single in-flight slot is reused; otherwise retire the entire lease and discard late data by request and connection incarnation. `spawnProcess` does not provide this stream/deadline/termination contract itself; the TW-06T owner must implement it.

### Proposed source high-water, projection eligibility, and clocks

**High-water ownership candidate:** TW-06 main/cache owns a durable source high-water record partitioned by `(execution-host identity, full profile tuple, authorityId, ledgerEpoch)`, not TW-06P, TW-06T, renderer, or the agent-status store. Store `(ledgerRevision, projectionSequence, catalogDigest)` atomically. On equal tuple, same digest is acceptable and different digest is `source_equivocation`; on lower order return `source_revision_regression`; on greater order advance the record only after full framing, fatal UTF-8 decode, strict semantic/digest validation, canonical wire byte equality, and passage through the finite admission barrier. The high-water commit and snapshot publication are one serialized admission point. `source.bind` may identify the epoch but cannot seed or advance this record. A first-seen record can be bootstrapped only from an explicitly admitted binding plus a complete validated `snapshot.read`; that adoption rule remains **OPEN** under P3. Connection/service restart changes the connection incarnation but never resets this record. Application restart drops any current label and matched overlay, retains high-water, and requires a fresh authenticated read before current can return. A post-admission stream violation retires the lease and revokes current plus its matched overlay, while preserving a valid committed high-water. **OPEN:** persistence location, first-seen bootstrap, detectable loss/corruption recovery, explicit rebind semantics, and whether equivocation/auth failure also hides historical stale display. If history is missing/corrupt for a previously bound partition, the candidate is unavailable until an explicit rebind decision; never silently treat it as first-seen.

**Projection eligibility candidate (not source fact):** the snapshot schema carries neither catalog `disposition` nor role `transition`, so omission is the simplest way to prevent retained refs being laundered into a live owner match. For ticket `disposition: pruning|pruned` or lifecycle `tearing-down|removed`, retain display rows but omit the separate ticket `coordinatorTarget` **and every workspace `target`**, set every workspace `referenceState: unavailable`, and emit no actions. For an otherwise eligible ticket, omit a workspace target and set its `referenceState: unavailable` for (a) repository `actualRole: excluded`; (b) repository actual state `absent|removing`; and (c) a transition whose `targetRole` is `excluded`. Keep the **current** `workspaceRef` for other open/eligible rows even if a non-exclusion transition exists; never substitute `transition.targetWorkspace` for it. This preserves the reviewed distinction between the current reference and a pending role goal. The catalog carries ticket disposition and coordinator ref separately from repository transition, role/state and workspace ref ([`ticket-catalog-v1.ts`](../../../ticket-workspace/packages/contracts/src/ticket-catalog-v1.ts#L44)); its planner gates ticket plannability on open disposition and lifecycle, then copies current `workspaceRef` separately from transition metadata ([`ticket-workspace-plan-v1.ts`](../../../ticket-workspace/packages/cli/src/ticket-workspace-plan-v1.ts#L133)). **OPEN:** owners must ratify the exact predicate, `availability` meaning for displayed but target-suppressed rows, and whether to omit targets or instead add a separately authenticated same-read eligibility record.

**Same-read match/click candidate:** each initial live match and click-time rebind starts with a **new** `snapshot.read.v1` on the existing authenticated lease; it must not use a cached display snapshot as fresh source evidence. For each operation, the producer performs one new catalog read and projects source tuple plus target eligibility from that same value. Main compares authority, epoch, ledger revision, sequence, catalog digest, ticket key, repository ID and the exact current `WorkspaceRef`/Orca owner tuple to the selected display snapshot. A changed source tuple, suppressed coordinator/workspace target, or changed reference returns unavailable pending snapshot refresh. Fresh observation timestamps may change `snapshotRevision`, so the match/click comparison uses the source tuple and exact reference, not snapshot-revision equality. No renderer-supplied ref/path or separate one-shot CLI/source read participates. The owner binder/capture remains separately bounded by one lease and an outer deadline.

**Earlier SSH/mixed-host candidate (historical):** the prefix-only classification and retention of an eligible SSH target are superseded by logical-v1 P5 and the [projection vectors](./resident-ticket-projection-vectors.md). Logical v1 classifies opaque IDs against separate exact setup-bound allowlists before P4 suppression. It omits nonallowlisted targets; an unsuppressed nonallowlisted workspace ref has `referenceState: unsupported`, while a P4-suppressed row has `referenceState: unavailable`. Either way, the ticket stays `unsupported` and pinned admission makes the whole snapshot unsupported. Production still needs verified ticket-ID-to-physical-host mapping, including no-ref remote cases. SSH contact loss remains `unverifiable` under [the SSH boundary](../ssh-execution-boundary.md).

**Clock/currentness candidate:** producer `generatedAt` is its source-clock time immediately after the bound catalog read, and `staleAfter` is `generatedAt` plus a fixed source TTL (candidate: 60 seconds). Do not compare either timestamp to Windows `Date.now()` or pass a Windows wall clock to `admitTicketNavigatorSnapshotV1(fixedNow)`: that helper directly compares the timestamp strings as wall time and no WSL clock handoff is proven. Currentness instead comes from the authenticated per-request fresh-read binding plus Orca main's monotonic request deadline; a validated receipt may remain current only for a host-owned monotonic cache TTL (candidate: 30 seconds), with no current after timeout, app restart, lease retirement, binding change or source high-water failure. `generatedAt`/`staleAfter` are validated display/source metadata, not proof of freshness; the consumer can validate their exact 60-second interval without comparing clock domains. **OPEN:** ratify source TTL, host cache TTL, exact timestamp semantics and suspend/resume behavior. If owners require cross-clock age comparison, specify a separately measured offset/uncertainty protocol before using it.

**Logical-v1 normative contract.** This exact contract replaces the earlier abbreviated message and proof formulas in this document for the injected logical protocol. It does not prove a production endpoint or credential handoff.

#### Strict hello schemas and proof transcript

Every object below is strict: it has exactly the listed fields, with no unknown or duplicate keys. `Identifier` means a non-empty string of at most 255 UTF-8 bytes, matching the pinned ticket `IdentifierV1` bound, with NUL forbidden for wire binding identifiers. `B64_16` and `B64_32` mean canonical unpadded base64url encodings of exactly 16 and 32 bytes respectively (22 and 43 ASCII characters); decoding and re-encoding must be byte-identical. `HexSha256` is exactly 64 lowercase hexadecimal characters. The profile, host and service fields are compared by exact value to Orca main's independently configured setup tuple.

```ts
type Profile = { profileId: Identifier; schemaVersion: 1; profileVersion: Identifier }
type Binding = {
  profile: Profile
  authorityId: Identifier
  executionHost: { kind: "wsl"; machineId: Identifier; distro: Identifier }
  expectedService: {
    producerName: "ticket-workspace"
    releaseId: Identifier
    artifactSha256: HexSha256
  }
}
type Capabilities = ["no-start.v1", "snapshot.read.v1", "source.bind.v1"]

type ClientHello = {
  type: "clientHello"; protocolId: "ticket.navigator.resident"; protocolVersion: 1
  sessionId: B64_16; clientNonce: B64_32; binding: Binding
  capabilities: Capabilities; proof: B64_32
}
type ServerHello = {
  type: "serverHello"; protocolId: "ticket.navigator.resident"; protocolVersion: 1
  sessionId: B64_16; clientNonce: B64_32; serverNonce: B64_32
  connectionIncarnation: B64_16; binding: Binding
  capabilities: Capabilities; proof: B64_32
}
type ClientFinish = {
  type: "clientFinish"; protocolId: "ticket.navigator.resident"; protocolVersion: 1
  sessionId: B64_16; clientNonce: B64_32; serverNonce: B64_32
  connectionIncarnation: B64_16; proof: B64_32
}
```

V1 accepts only the exact ordered capability tuple shown above; the server echoes it byte-for-byte as an array. There is no subset negotiation or unknown capability tolerance. Both peers require protocol v1 semantics. A peer that cannot provide all three capabilities, the exact profile/authority/WSL/artifact binding, or the exact v1 contract closes the handshake; it does not send an unauthenticated error or downgrade. `serverHello` echoes `sessionId`, `clientNonce`, and the full `binding`; its `serverNonce` and `connectionIncarnation` are fresh. `clientFinish` echoes the exact session, both nonces, and incarnation from the two preceding messages.

The setup key is exactly 32 random bytes and is injected into both peers; how production creates, stores, hands off, rotates and revokes it remains open. Let `CH`, `SH`, and `CF` be the corresponding hello objects with only their `proof` property removed. The proof fields are canonical unpadded base64url HMAC-SHA-256 outputs over these exact canonical JSON values (the domain strings are case-sensitive):

```text
clientProof = HMAC(setupKey, UTF8(canonicalJsonV1({
  domain: "ticket.navigator.resident.v1/clientHello", clientHello: CH
})))
serverProof = HMAC(setupKey, UTF8(canonicalJsonV1({
  domain: "ticket.navigator.resident.v1/serverHello",
  clientHello: CH, clientProof, serverHello: SH
})))
clientFinishProof = HMAC(setupKey, UTF8(canonicalJsonV1({
  domain: "ticket.navigator.resident.v1/clientFinish",
  clientHello: CH, clientProof, serverHello: SH, serverProof, clientFinish: CF
})))
```

All proof comparisons are constant-time. A `clientHello` replay cannot answer a fresh server nonce; a finish proof is valid only for the one live challenge and exact incarnation. The server grants no lease before it verifies `clientFinishProof`; the client sends no protected request before it verifies `serverProof`.

#### Canonical bytes, transcript key and protected framing

Use the ticket `canonicalJsonV1` implementation at submodule pin `54477c2371094f1cbc438845fdfde0ca3584e2aa`: object keys sort by JavaScript UTF-16 code-unit order, arrays preserve order, and numbers must be safe integers. Strings use the pinned JavaScript JSON string escaping, with no Unicode normalization. Wire JSON is UTF-8 with no BOM, whitespace or trailing newline. Reject invalid UTF-8, duplicate object keys, unsafe/fractional numbers, unknown fields, and any body whose parsed value does not reserialize byte-for-byte to the received canonical bytes. This includes numeric-looking object keys and supplementary Unicode keys; the vector fixture demonstrates their UTF-16 ordering.

Hello wires are `uint32be(N) || body`, where the four-byte unsigned big-endian length counts only the canonical JSON body; no hello has a trailer. After successful `clientFinish`, define `CF` as above and:

```text
T = SHA256(UTF8(canonicalJsonV1({
  clientHello: CH, clientProof, serverHello: SH, serverProof,
  clientFinish: CF, clientFinishProof
})))                 // T is the raw 32-byte digest

K_c2s = HKDF-SHA256(IKM=setupKey, salt=T,
  info=UTF8("ticket.navigator.resident.v1/frame/c2s"), L=32)
K_s2c = HKDF-SHA256(IKM=setupKey, salt=T,
  info=UTF8("ticket.navigator.resident.v1/frame/s2c"), L=32)
```

HKDF is RFC 5869 extract-and-expand with SHA-256. For a post-finish frame, `body = UTF8(canonicalJsonV1(message))`, `N = body.length`, and the wire is `uint32be(N) || body || tag`; the trailer is exactly 32 raw bytes. Before allocation, the receiver requires `1 <= N <= 24,576`, the maximum body of any v1 frame. It then authenticates and parses the bounded body; after reading its strict `type` discriminant, it additionally requires `N <= 4,096` for every control message. `snapshot.chunk` may use up to 24,576 bytes. Hello frames are control and are capped at 4,096 before allocation. The HMAC preimage is the following concatenation, with no other separators:

```text
UTF8("ticket.navigator.resident.v1/frame") || 0x00 || T || directionByte ||
UTF8(sessionId) || 0x00 || UTF8(connectionIncarnation) || 0x00 ||
uint64be(sequence) || uint32be(N) || body
tag = HMAC-SHA256(K_direction, preimage)
directionByte = 0 for c2s; 1 for s2c
```

`sessionId` and `connectionIncarnation` are the exact ASCII base64url strings from the verified hello. The sequence is not transmitted: each direction independently starts at unsigned 64-bit zero on the first frame after finish, and the receiver authenticates exactly its next expected value. Increment only after the complete frame is emitted/verified; there is no wrap. A duplicate, gap, replay, malformed length, bad tag, invalid message order, or extra/trailing byte retires the lease. Tags are compared in constant time. A per-frame MAC provides integrity and replay ordering only for a peer holding the expected key; it does not prove the executable or trusted key delivery, and it does not encrypt or conceal snapshot bytes. Production P1 must prove endpoint access/privacy against unintended readers as well as integrity.

#### Protected message union

The following are the complete v1 message shapes. Each newly allocated `source.bind` or `snapshot.read` request ID is a fresh `B64_16` and is never allocated again in that process/session. Its response frames and any `cancel` for that in-flight read must echo the same ID. Integer bounds are inclusive. Every field is required and no extra field is accepted.

| Direction | Exact message shape | Meaning / terminal rule |
| --- | --- | --- |
| c2s | `{ type: "source.bind", requestId: RequestId, profile: Profile, authorityId: Identifier, deadlineBudgetMs: integer[1..5000] }` | Setup only; exactly one after finish. It performs one fresh validated source read, discovers the epoch, and never seeds high-water. |
| s2c | `{ type: "source.bound", requestId: RequestId, authorityId: Identifier, ledgerEpoch: Identifier }` | Must match the bind request and exact expected authority; successful bind establishes the lease epoch. |
| c2s | `{ type: "snapshot.read", requestId: RequestId, profile: Profile, authorityId: Identifier, ledgerEpoch: Identifier, deadlineBudgetMs: integer[1..10000] }` | One outstanding request on a bound lease; profile, authority and epoch must equal its binding. |
| s2c | `{ type: "snapshot.begin", requestId: RequestId, snapshotBytes: integer[1..2097152] }` | Starts a response only after the producer has fully validated and bounded the canonical snapshot. |
| s2c | `{ type: "snapshot.chunk", requestId: RequestId, index: integer[0..127], bytes: canonical unpadded base64url }` | Decodes to 1..16,384 bytes. Indices are contiguous from zero; every non-final chunk is exactly 16,384 bytes; no more than 128 chunks. |
| s2c | `{ type: "snapshot.end", requestId: RequestId, byteCount: integer[1..2097152], chunkCount: integer[1..128] }` | Exactly one successful terminal; both counts must equal the begin declaration and accumulated chunks. |
| c2s | `{ type: "cancel", requestId: RequestId }` | Cancels only that in-flight read; never stops the resident service or ticket resources. |
| s2c | `{ type: "cancelled", requestId: RequestId }` | Authenticated terminal means work is settled and no later frame for that request may arrive. |
| s2c | `{ type: "error", requestId: RequestId, code: ErrorCode }` | Authenticated terminal for a settled request; no free-form text or diagnostics. |

`ErrorCode` is exactly one of `binding_mismatch`, `authority_rebind_required`, `source_unavailable`, `snapshot_too_large`, or `deadline_exceeded`. These are the only v1 protected wire errors. Authentication, malformed JSON/schema, capability/version mismatch, bad message order, and duplicate request IDs close the lease without an error frame. `source_equivocation` and `source_revision_regression` are Orca TW-06 admission outcomes, not producer wire errors. An error or successful terminal settles the one outstanding request; `authority_rebind_required` retires the lease and requires explicit setup/rebind. A cancel race has one terminal only (`cancelled`, a valid completed response, or an error); cancellation never extends the original deadline, and no cancelled response is admitted.

For a read response, only `snapshot.begin`, one or more matching contiguous chunks, and one matching `snapshot.end` may follow the request. The producer sends no partial snapshot on error. The consumer decodes only within the exact 2,097,152-byte cap, validates the ticket-owned snapshot and digest, and requires canonical payload bytes before admission. A complete or partial trailing frame observed in the same delivered byte batch after `snapshot.end` but before admission rejects the candidate with no high-water change. After admission, any unsolicited byte retires the lease and revokes live current plus its matched overlay without rolling back committed high-water.

#### State, deadlines, and artifact compatibility

The lease state is `closed -> hello -> authenticated-unbound -> bound-idle -> read-in-flight -> bound-idle`; any authentication, stream, ordering, or timeout ambiguity transitions to `closed`. Orca main may enter `hello` only through explicit setup over an already-open duplex. A read accepts only the existing bound lease and makes zero process, WSL, endpoint-probe, attach, or reconnect calls. The handshake is not a readable lease: `source.bind` must return a matching `source.bound` before the first snapshot read. Bind does not adopt or update durable high-water.

Orca main starts one monotonic 5,000 ms setup deadline immediately before the first hello transport work. It covers all three hello messages and `source.bind`; before sending bind, `deadlineBudgetMs` is the floored positive remaining milliseconds, capped at 5,000 (the vector uses 5,000 for an immediate bind). Each snapshot read gets one monotonic 10,000 ms end-to-end deadline started before its first transport write and sends only the floored positive remaining budget, capped at 10,000. Neither peer may extend a deadline. The client retires the lease if a terminal cannot be authenticated and settled by the original deadline; it cannot reuse the stream slot while a cancel is ambiguous. A timeout or contact loss is unavailable/unverifiable and never evidence that remote work exited.

`expectedService.releaseId` and `expectedService.artifactSha256` come from an independently verified installed artifact manifest; `serverHello.binding` must echo them exactly, and the authenticated snapshot's `producer.version` must equal that release ID. A package version, self-reported digest, path, PID, or hello echo does not prove artifact identity. Production still requires verified TW-M1P runtime/profile provenance and TW-06P artifact provenance plus a trusted secret handoff. A newer producer is compatible only if it implements this exact v1 contract; otherwise it fails closed without downgrade.

The deterministic inputs and expected hello bodies/proofs, transcript digest, HKDF keys, protected frame bytes/tags, and Unicode/numeric-like key ordering are in [`resident-ticket-transport-v1-golden-vectors.json`](./resident-ticket-transport-v1-golden-vectors.json). Recompute with the pinned `canonicalJsonV1`, HMAC-SHA-256, RFC 5869 HKDF-SHA-256, four-byte big-endian lengths, and the preimages above; the fixture records successful Node built-in crypto, `@noble/hashes` and independent Python standard-library checks.

**Implementation boundary after this packet and golden vectors pass independent review:** The continuing TW-06P Luna may implement a private pure projector plus injected reader/clock/key/duplex request handler. The continuing TW-06T Luna may implement an Orca-main injected fake-duplex handshake/client returning bounded transport bytes. Their tests must share deterministic golden handshake/frame vectors, byte caps, failure codes and timing cases. Neither worker may launch WSL, create a production lease, edit fixture IPC/preload/renderer, publish `current`, advance durable high-water, assert an Orca owner match, or implement effects. TW-06 main/cache and TW-02L own those later joins. Production setup remains behind its separate proofs above.

## Review checklist for the protocol gate

- Reads and renderer refreshes make zero WSL/CLI/coordinator start attempts, including disconnected and retry paths.
- Wrong or replayed auth, profile, authority, machine/distro, epoch, version, capability, request ID, or connection incarnation fails closed.
- Every accepted response is tied to one fresh bound catalog read; changed `catalogDigest` for the same source tuple is rejected. Repeated reads of an unchanged catalog may regenerate timestamps with stable sequence semantics.
- Exactly 2 MiB is admitted for further validation; the first byte over the limit cancels before unbounded buffering. Invalid split UTF-8 is rejected fatally.
- A mixed local/SSH projection marks the ticket unsupported and SSH reference unsupported while local references remain unavailable. A valid catalog whose projected snapshot exceeds 2 MiB returns unavailable without partial bytes.
- Timeout/cancellation, short stream, pre-admission malformed response, or disconnect does not replace the last verified candidate or release an in-flight request before its stream is settled/retired. A post-admission stream violation retires the lease and revokes live current/overlay without rolling back valid durable high-water.
- Epoch change requires explicit rebind; source revision/projection regressions are rejected; transport hashes are never treated as authentication.
- Main/preload use the same full ticket-owned runtime semantic validator, including uniqueness, SSH presentation, and digest checks; secrets, paths, raw diagnostics, and Orca-private evidence do not cross the boundary.
- Tests assert no WSL/CLI/process-launch call from the read path and do not launch or reveal an Electron window.
