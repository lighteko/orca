# TW-06P Producer / TW-06T Resident Transport Contract

- **Status:** Decision draft; no implementation is authorized by this document.
- **Source pin:** `ticket-workspace` commit `2045808ffdb6baead2e659855cefb02f7b36491c`.
- **Proposed protocol:** `ticket.navigator.resident`, version 1.
- **Scope:** One Orca desktop and its configured local WSL coordinator. SSH, paired runtime, relay, `orca serve`, and mobile clients remain outside this first slice.

This contract separates the ticket-owned snapshot producer from the Orca-owned connection lifecycle. A snapshot read may use only an already authenticated, already resident connection. It must never start WSL, the ticket CLI, a shell, or the coordinator. The snapshot digest checks content consistency; it does not authenticate the producer.

## Recommended ownership split

| Owner                         | Contract responsibility                                                                                                                                                                                                                                                        |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| TW-06P ticket package         | Own the production projector and the canonical `TicketNavigatorSnapshotV1` schema/digest. Read through the ticket authority's validated catalog capability. Do not publish Orca agent status or internal Orca binding tokens.                                                  |
| TW-06T Orca main integration  | Own the explicit setup/enable authority, authenticated resident connection lease, host/profile/authority binding, connection lifecycle, no-start read gate, cancellation, and bounded byte accumulation. Only this layer may decide whether setup can launch or attach to WSL. |
| TW-06 main/preload workstream | Own the renderer-facing IPC request/result, main cache/admission, strict outgoing wire, and second preload validation. Receive no transport handle or secret in preload.                                                                                                       |
| Renderer                      | Consume only the TW-06 validated read-only result. Snapshot action descriptors are not mutation authority.                                                                                                                                                                     |

This split follows the plan's ownership layers: the ticket package owns ticket catalog/projection, Orca owns host execution and integration, and preload/renderer present validated data. The setup actor is a **proposed decision**: an explicit Orca main command/handler may establish the resident connection; a read/refresh command may not. The ticket producer owns the service-side identity and snapshot response. Do not extend the terminal daemon or agent-status store into a ticket state owner.

### Reuse seam assessment

- Reuse the daemon's _protocol lessons_—semantic versioning, authenticated hello, bounded handshake wait, and endpoint ownership review—if useful. Its terminal daemon process, endpoint path, token lifecycle, and socket ownership protocol are coupled to terminal preservation and are not justified as the ticket service implementation.
- The WSL hook relay already has a bidirectional channel, but its manager ensures it from PTY lifecycle, and its server/relay own agent-hook ingestion. Reusing that manager or status receiver would violate the proposed explicit setup owner and risk folding ticket state into the agent-status path. No current WSL hook seam is a drop-in ticket connection owner.
- `buildWslExecArgs` remains the correct argv rule if an explicit setup action is later authorized to launch a WSL child. It is not a no-start read primitive and supplies neither authentication nor resident lifecycle ownership.

**Recommendation:** implement against a small main-owned resident-connection interface whose lease is established by explicit setup; keep the service protocol technology-neutral until the endpoint and credential handoff decisions are frozen. The inspected Orca precedents justify lifecycle and authentication requirements, but not selecting a specific endpoint technology.

## Version 1 logical protocol

The wire protocol is named `ticket.navigator.resident` and has an independent semantic version, separate from the Orca runtime protocol and ticket package version. Version 1 has a strict handshake, a read-only snapshot request, a bounded byte response, cancellation, and typed failure. The endpoint may use any transport later selected by its owners; this contract does not select TCP, named pipes, stdio, HTTP, or a relay.

### Setup and authentication

1. A separate, explicit setup/enable action creates or attaches the resident producer, provisions its authentication material, and returns an **in-memory** authenticated connection lease to Orca main. Only that action may launch WSL or the producer. Setup must identify its target from configured Orca execution-host/profile data, not from renderer-supplied paths.
2. The lease is bound to one Orca installation/session incarnation and exactly one configured tuple: ticket profile `(profileId, schemaVersion, profileVersion)`, expected ticket `authorityId`, and coordinator execution host `(machineId, kind: wsl, distro)`. `stateRoot`, ledger path, endpoint path, and credential reference are not protocol identity fields and are not sent to the renderer.
3. The hello authenticates both peers and negotiates a common protocol version and the required `snapshot.read.v1` plus `no-start.v1` capabilities. `no-start.v1` means the service-side read does not start WSL, a CLI, a shell, coordinator, or child process. Nonces correlate/authenticate a connection and prevent hello replay; they do not prove that a catalog read is fresh. A path, loopback address, PID, endpoint file, `catalogDigest`, or `snapshotRevision` alone is not authentication or source freshness.
4. The authenticated service reports its producer identity/version, profile tuple, authority ID, current ledger epoch, coordinator host identity, connection incarnation, and negotiated capabilities. Orca compares these with its configured/explicitly bound values before marking the lease readable. Missing proof, a mismatch, a version gap, an unsupported profile, or a missing capability leaves it unavailable.
5. Authentication material is setup-owned, scoped to this profile/authority, revocable/rotatable, and never placed in argv, renderer IPC, snapshot JSON, ordinary logs, or diagnostics. The exact secret storage and handoff mechanism remains open until endpoint technology is selected.

The authenticated session establishes who answered. Request IDs bind response bytes to one request. Neither session nonces, request IDs, nor snapshot digests prove that the producer observed the current catalog for that request. Freshness requires the bound source read and tuple rules below.

## Minimum source-side projection proposal

The first production producer should perform exactly one fresh, authority-bound `TicketWorkspaceCatalogReaderV1.read(capability)` for each `snapshot.read.v1` request and project from that exact validated catalog value. Reusing a prior catalog/snapshot for a new request is not permitted. An equivalent source-owned observation proof is acceptable only if it proves the same current authority/profile/epoch/revision and exact catalog bytes. It should not call `status` or any CLI as a subprocess per read, start a coordinator, query provider APIs, or inspect Orca state. A failed/untrusted catalog read yields a typed unavailable response, never an empty catalog snapshot.

- Copy the ticket key, title/label, lifecycle, orchestration correlation, repository ID, display name, `actualRole`, actual state, branch, and ticket-owned `WorkspaceRef` claims from that catalog. Set snapshot workspace `role` from catalog `actualRole`; `desiredRole` is a transition goal and must not be presented as current. A pending role transition remains separately visible only through a later reviewed DTO; it grants no action authority. Enforce the existing unique ticket/repository identities and strict DTO bounds.
- For a supported local-only projection, set ticket `availability: 'available'` to mean that the ticket catalog can be presented; it does not assert Orca workspace readiness, plan completeness, or effect authority. If its coordinator target or any workspace target has an `executionHostId` beginning `ssh:`, set ticket `availability: 'unsupported'`; set each SSH workspace's `referenceState: 'unsupported'`. In a mixed local/SSH ticket, local workspace `referenceState` remains `unavailable` until Orca proves its exact owner join, while the SSH workspace stays unsupported. This follows the pinned runtime validator's presentation rule. Even if fixture admission reports `mutationAllowed: true`, the initial producer emits no actions and the live root gateway remains mandatory for every effect.
- Until TW-02's exact owner mapping is implemented, use `referenceState: 'unavailable'` for local workspace targets. A target is a ticket claim; only Orca's owner resolver can prove `matched`. A ticket `coordinatorRef` is not proof of an Orca Run or pane binding.
- Use `enrichment: { issue: 'unknown', mergeRequests: 'unknown' }` and empty action arrays in the minimal read-only producer. It introduces no provider query or action authority. Later action descriptors remain presentation hints and must be frozen by TW-06.
- Copy `authorityId`, `ledgerEpoch`, and `ledgerRevision` from the validated catalog. Compute `catalogDigest` as the digest of its canonical bytes. Under the trusted ledger CAS writer, a fixed `(authorityId, ledgerEpoch, ledgerRevision)` has one canonical catalog digest; a previously observed different digest at that same tuple is equivocation and returns unavailable. For this catalog-only projection, keep `projectionSequence: 0`: ledger revision plus catalog digest determines catalog-derived ticket/workspace fields under fixed v1 projection rules. Producer version metadata and observation times may change independently and therefore change `snapshotRevision`. Adding a dynamic source requires a new producer-owned monotonic sequence contract first.
- `generatedAt` is the UTC time immediately after the fresh bound catalog read; `staleAfter` is `generatedAt` plus the fixed TTL. Repeated reads of an unchanged source tuple may regenerate those two observation times without changing `projectionSequence`; `snapshotRevision` then changes because it is the canonical digest of the full snapshot. The response still represents a fresh read, not a cached snapshot. TTL and acceptable WSL-to-Windows clock handoff remain explicit decisions below.
- After projection, run the full runtime contract validator and measure the canonical UTF-8 snapshot. If an otherwise valid catalog projects to more than 2 MiB, return typed unavailable with no partial snapshot. The catalog's larger input limit does not relax the navigator snapshot cap.

This conservative starting shape can display supported ticket catalog entries while keeping local Orca references unavailable until the separate owner join is proven. SSH entries remain visibly unsupported. It does not expose a public `clear` verdict or authorize an action.

### Source freshness and TW-02 currentness handoff

The producer's fresh read and tuple rules, not its nonce or request ID, establish source freshness. A valid authenticated server must bind each response to the exact catalog returned by that request's validated catalog read. For a repeated `(authorityId, ledgerEpoch, ledgerRevision, projectionSequence)`, a different `catalogDigest` is equivocation and unavailable. A same-tuple response may have new `generatedAt`/`staleAfter` values only when it was generated from a new bound read; those metadata changes intentionally produce a different `snapshotRevision`.

`snapshotRevision` is the digest of the complete serialized snapshot, including those observation timestamps. It is not a stable owner-version token across separate fresh reads. **Cross-draft recommendation for TW-02:** after binder/capture, compare profile, authority, epoch, ledger revision, projection sequence, catalog digest, and the exact relevant `WorkspaceRefV1` plus repository ID/owner tuple. Do not require a new producer read to have the same `snapshotRevision`; that would conflict with fresh per-request observations. Keep `snapshotRevision` for validating one exact snapshot and for binding the separate Orca overlay below. TW-02's owner binding remains the authority for whether the reference matched.

### Read and response

Logical request:

```text
snapshot.read.v1 {
  requestId,
  profile: { profileId, schemaVersion: 1, profileVersion },
  authorityId,
  ledgerEpoch,
  deadlineBudgetMs
}
```

The request is accepted only on the current authenticated lease and only when profile, authority, and epoch equal the lease's explicit binding. On first setup, the binding must be established by that explicit setup handshake; a snapshot response cannot silently rebind an existing cache partition. A changed ledger epoch returns `authority_rebind_required`. Rebinding is a separate explicit decision and invalidates current status for the prior binding.

The ticket producer returns the exact UTF-8 JSON bytes of one `TicketNavigatorSnapshotV1`. The source authority, profile, and epoch in the payload must equal the authenticated request/session. The producer derives `ledgerRevision`, `projectionSequence`, `catalogDigest`, `generatedAt`, and `staleAfter` from the source observation; it must not refresh timestamps on Orca receipt or reuse an older snapshot as current. Orca rejects decreasing `(ledgerRevision, projectionSequence)` under the source corpus ordering rule. The producer does not claim an Orca `WorkspaceRef` owner match; TW-02's exact join and `repoId` equality check remain separate.

The transport frames a response as one request-correlated start, zero or more byte chunks, and one terminal completion carrying the total byte count. The specific byte framing is an implementation decision, but chunk boundaries must not affect the JSON bytes or UTF-8 decode. The consumer:

- requires the start to carry the request ID and a declared byte length no greater than the cap; the terminal completion repeats the request ID and exact received byte count;
- checks each incoming chunk incrementally and cancels immediately if accumulated snapshot bytes would exceed **2,097,152**; it does not buffer an unbounded body and measure afterward;
- rejects an announced length above the same limit before accepting chunks, while still enforcing the running count because a length claim is untrusted;
- requires one matching completion and an exact final byte count; a close, cancellation, duplicate completion, wrong `requestId`, trailing response, or short body rejects the whole candidate;
- performs fatal UTF-8 decoding once the bounded byte sequence is complete, then strict JSON/schema validation and digest verification; malformed UTF-8, JSON, schema, provenance, or digest never reaches preload;
- keeps framing/control metadata separately bounded and does not count it as snapshot JSON. V1 metadata and error reason codes are strict and small; free-form diagnostics are not carried in the response.

No partial payload replaces the current snapshot. The schema's per-field/array/aggregate limits still apply after the transport byte cap.

### Cancellation and deadline

Each read has one Orca-main-owned monotonic deadline established before transport work starts; endpoint lookup, automatic reconnect, WSL command execution, and CLI launch are forbidden in this path. Send only the remaining budget to the producer; neither peer can extend it. A cancellation or deadline sends `cancel(requestId)` when negotiated. The producer should stop projection/serialization/read work and acknowledge settlement. If settlement cannot be established, Orca retires that connection lease, discards late frames by request/connection incarnation, and does not admit a second read on the ambiguous stream. Cancellation of a read does not stop the resident service, terminals, coordinator, or ticket resources.

**Proposed initial bound for TW-06T to ratify:** 10 seconds end-to-end for a resident snapshot read, with a shorter separately bounded hello during explicit setup. The exact number must be covered by a measured slow/2 MiB stream test before implementation is declared done. The deadline contract is mandatory even if the value changes.

### No-start proof and failure results

`readSnapshot()` is available only through an already-established in-memory lease carrying an authenticated connection incarnation and negotiated `no-start.v1` capability. If the lease is absent, stale, unauthenticated, mismatched, or disconnected, return transport-unavailable immediately. The capability is a negotiated service contract, not by itself proof about Orca main's call graph: implementation proof requires the read method to take only the existing lease and a no-launch request port, plus tests that assert no process/WSL/CLI start calls on connected, disconnected, retry, and cancellation paths. The producer read likewise has no child-process or coordinator-start path. It must not call a generic `ensure*`, process launcher, `runProcess`/`spawnProcess`, `wsl.exe`, shell, CLI `status`, or endpoint startup/probe that can create a resident process. It must not silently answer from Windows/native catalog files or another configured profile. A future reconnect path is setup/lifecycle work and must have its own explicit authority; read retry alone cannot reconnect.

All of these reject the candidate and produce unavailable/stale presentation through TW-06: no lease, no no-start capability, auth failure, no common protocol/capability, wrong profile/authority/host/epoch, revision regression, oversized body, malformed UTF-8/JSON/schema/digest, partial stream, cancellation, timeout, or disconnect. Errors carry stable bounded reason codes only. An old last-verified result may be presented stale by TW-06's separately frozen cache contract, partitioned by `(profileId, authorityId, ledgerEpoch)`; it never becomes current because contact returned or a digest matched. Transport loss says nothing about remote process exit. If SSH is added in a later scope, contact loss remains `unverifiable` under the SSH boundary.

### Mixed versions

- Negotiate the highest mutually supported semantic protocol version and required capabilities in hello. Never infer support from the ticket package's version string alone.
- Version 1 requires `TicketNavigatorSnapshotV1` contract/schema version 1. Unknown major versions, fields, message kinds, or capabilities fail closed; no fallback to the one-shot status CLI or a weaker transport.
- Keep v1 envelope shapes strict. Any new field, new message kind, or changed meaning needs a new protocol/schema version or an explicitly negotiated capability with a safe older-peer fallback. Do not ship an unnegotiated stream opcode on an Orca paired wire.
- A newer producer may serve v1 only when it can emit the exact v1 projection and semantics. If it cannot, return a version/capability failure. An older consumer must never accept new content merely because it is valid JSON.
- `producer.version` is informational and checked against a TW-06-supported compatibility policy. The package-version range/policy is still a decision; wire capability/schema version is authoritative.

### Privacy and ownership exclusions

- Never serialize `stateRoot`, ledger/checkout paths outside fields already allowed by the ticket DTO, endpoint locator, auth material, command line, stderr, raw validation issues, cache internals, Orca binding tokens, Run/pane evidence, TW-01 observation IDs/timestamps, or agent-status records into protocol diagnostics or preload data.
- Do not log complete snapshots or tokens. Logs may contain connection incarnation hashes only if redacted and bounded, stable reason codes, byte counts, negotiated protocol, and non-secret profile/authority IDs under the existing redaction policy.
- Preserve existing `WorkspaceRefV1` fields as ticket-owned claims; only an Orca owner resolver may attest them. `snapshotRevision`/`catalogDigest` can detect mismatch or regression but cannot authorize actions or replace authentication.
- The producer publishes ticket-owned projection only. Agent/session state remains in Orca's existing execution-host-owned status store. No ticket status store, message bus, liveness vocabulary, or mutation authority is added.

## TW-06 main/preload handoff

TW-06 starts after the producer and transport packets plus their shared protocol are frozen. Its main-side port should consume only `readSnapshot(lease, signal, deadline)` and a bounded byte stream plus private authenticated peer evidence. TW-06 main owns strict snapshot validation, current/stale/unavailable projection, cache partition/rebind behavior, and outgoing wire provenance. Main and preload must run the same full ticket-owned runtime semantic validator, not JSON Schema alone: strict DTO/field bounds, unique ticket and repository IDs, SSH presentation rules, canonical UTF-8 size, and canonical `snapshotRevision` digest equality. The generated JSON Schema artifact is useful for shape/documentation but does not implement all these semantic checks. Main fatally decodes bounded transport bytes before JSON parsing; preload checks the exact UTF-8 byte size and runs the same semantic validator after IPC. The validator must be renderer-neutral and consumed from one ticket-owned runtime artifact; do not copy the semantic rules into separate main/preload implementations.

The ticket snapshot is immutable after ticket producer validation. Orca's TW-02 resolution result is **not** written into `TicketNavigatorSnapshotV1`, and Orca must not recalculate or replace the ticket-owned `snapshotRevision`. Define a separate strict Orca-owned `OrcaTicketWorkspaceResolutionOverlayV1` with its own schema/version and validators. At minimum it carries `baseSnapshotRevision`, the matching source tuple, and unique `(ticketKey, repositoryId)` resolution rows (`matched`, `unavailable`, or `unsupported`). `matched` is emitted only from the exact Orca owner join. Preload validates the overlay independently and accepts it only when its base revision and source tuple equal the immutable snapshot being returned; otherwise it drops the overlay and leaves the conservative ticket reference states in force. Internal owner tokens, catalog capabilities, and run/pane evidence stay in main.

Preload treats the invoke value as unknown, validates it independently with the same ticket-owned runtime validator plus the separate Orca overlay validator, and returns only parsed renderer DTOs. Renderer requests cannot select a profile, authority, distro, path, or endpoint. No token, transport object, raw locator, or Orca internal evidence crosses preload.

The local ignored IPC draft proposes a zero-argument renderer call and `current` / `last-verified-stale` / Tickets-only `unavailable` results. TW-06 should review that proposal and publish its own tracked contract/fixture before implementation; neither TW-06P nor TW-06T adopts it by reference.

## Decisions required to issue implementation packets

1. **Freeze setup ownership:** ratify Orca main as the only explicit setup/enable actor and define start, attach, stop, app-restart, and user rebind behavior. No implicit startup or reconnection is permitted from a snapshot read.
2. **Select endpoint technology and auth handoff:** choose a transport that supports resident operation and per-connection authentication; decide where the secret is stored/delivered and how both peers prove identity. Existing daemon token and WSL relay are precedents, not approved reuse.
3. **Bind the authority tuple:** define how configured profile and Orca execution host map to ticket `authorityId`, how the first `ledgerEpoch` is admitted, and who confirms an epoch rebind. Keep workspace owner mapping for TW-02.
4. **Freeze producer freshness semantics:** define how `projectionSequence` advances, its relationship to ledger revision/catalog digest, snapshot TTL, WSL-to-Windows clock admission, and ticket `availability` semantics. Do not assume clocks are synchronized without a source-owned handoff.
5. **Ratify stream and deadline values:** choose exact v1 framing/control-message shapes, per-frame metadata bounds, the proposed 10-second read deadline, setup hello deadline, and cancellation settlement behavior. Keep raw payload cap at exactly 2 MiB.
6. **Freeze schema consumption:** choose a supported producer-version policy and how Orca main/preload consume the ticket-owned generated schema/corpus without a second handwritten schema owner. Private submodule/package access and untrusted-PR CI policy are separate release gates.

Once all six decisions are frozen, issue separate bounded ownership packets. **TW-06P** owns the ticket-repository producer/projection and service side. **TW-06T** owns the Orca main setup/authenticated no-start client and connection lifecycle, excluding IPC and UI. These packets may run in parallel against the frozen protocol and disjoint repositories/files. **TW-06** owns main/preload validation and IPC/cache contract after both producers are available. TW-06T must not touch agent-status ownership or transport technology selected for terminal/SSH lifecycles without an explicit reuse decision. TW-02's workspace owner mapping is a separate dependency for any claim that a snapshot target resolves to a live Orca workspace; TW-02 should compare the fresh source tuple and exact relevant ref as described above, not require snapshot digest equality across regenerated observations.

## Review checklist for the protocol gate

- Reads and renderer refreshes make zero WSL/CLI/coordinator start attempts, including disconnected and retry paths.
- Wrong or replayed auth, profile, authority, machine/distro, epoch, version, capability, request ID, or connection incarnation fails closed.
- Every accepted response is tied to one fresh bound catalog read; changed `catalogDigest` for the same source tuple is rejected. Repeated reads of an unchanged catalog may regenerate timestamps with stable sequence semantics.
- Exactly 2 MiB is admitted for further validation; the first byte over the limit cancels before unbounded buffering. Invalid split UTF-8 is rejected fatally.
- A mixed local/SSH projection marks the ticket unsupported and SSH reference unsupported while local references remain unavailable. A valid catalog whose projected snapshot exceeds 2 MiB returns unavailable without partial bytes.
- Timeout/cancellation, short stream, late response, disconnect, and malformed response do not replace the last verified candidate or release an in-flight request before its stream is settled/retired.
- Epoch change requires explicit rebind; source revision/projection regressions are rejected; transport hashes are never treated as authentication.
- Main/preload use the same full ticket-owned runtime semantic validator, including uniqueness, SSH presentation, and digest checks; secrets, paths, raw diagnostics, and Orca-private evidence do not cross the boundary.
- Tests assert no WSL/CLI/process-launch call from the read path and do not launch or reveal an Electron window.
